# 묶음 세션 — 청크 열 개를 한 번에 치는 프롬프트

토큰이 많이 남은 날, 청크 하나씩이 아니라 **열 개 안팎을 한 묶음으로 치고 마무리까지** 가는
세션의 여는 말이다. 아래 블록을 그대로 붙여넣고 마지막 줄의 토큰 비율만 채운다.

**청크 하나만 칠 때는 이것을 안 쓴다** — 그때는 `다음 청크 해` 한 줄이다.
**설계 행(`/design`)이 따로 있는 번들도 이것을 안 쓴다** — 그때는 `번들 해` 한 줄이고 `CLAUDE.md` 「번들 모드」가 규칙이다(계획 밖 갈림은 정하고 이력에 적는다). 이 여는 말은 **계획을 이 세션에서 세울 때**라 계획 밖 갈림에서 멈춘다 — 두 규칙이 갈리는 이유는 결정을 물은 자리가 이 세션이냐 설계 세션이냐다.

## 붙여넣는 것

```
/warmup

예열 끝나면 코드로 가지 말고 계획 모드로 들어간다. 이 세션은 청크 열 개 안팎을
한 묶음으로 치고 마무리까지 가는 것이 목표다.

[계획 단계에서 정할 것 — 여기서 다 정하고 실행 중엔 안 묻는다]
1. 지금 깨져 있는 것이 있나 먼저 본다. origin/main 의 CI 가 빨갛거나 진행중 청크가
   남아 있으면 그것이 묶음보다 먼저다.
2. .claude/explain-mode 가 있나 본다. 있으면 묶음을 치기 전에 어떻게 할지 정한다 —
   열 개마다 구조를 펴면 예산이 다 간다. 첫 청크에만 펴거나, 끄고 간다.
3. PLAN.md 분할표 미착수 행을 훑고 비용순(「잡을 수 있는 청크가 여럿일 때 무엇부터」)으로
   10개 안팎을 고른다. 고른 이유를 한 줄씩만 적는다.
   묶음에서 빼는 것: 손 줄이 입력인 것(마이그레이션 기동·e2e·프록시·시드·로그),
   측정값이 있어야 정해지는 것, 점검(단위가 청크와 다르다).
4. 고른 것을 주제로 묶는다. 같은 파일·같은 층·같은 축을 건드리는 것끼리 한 묶음이고,
   묶음 안에서 흡수할 수 있는 것을 흡수한다(흡수하면 상한도 같이 는다).
5. 그 열 개를 치면서 갈릴 결정을 전부 지금 한꺼번에 내민다. 선택지마다 득실과
   확장성 있는 쪽을 같이 적는다. 실행 중에 안 멈추는 것이 이 항목의 목적이다.
6. 이 묶음이 세우는 표·권한·문서를 **부르는 입구가 계획 안에 있나** 본다.
   스키마 청크를 여럿 묶으면 입구가 통째로 빠지는 것이 기본값이다 —
   아무도 못 채우는 표를 만들고 닫게 된다. 없으면 그 자리에서 청크를 세운다.
7. 마이그레이션 V 번호와 새로 세울 청크 번호 대역을 미리 예약해서 계획에 적는다.
8. 병렬이 되는지 아래 [병렬] 로 판단한다.
정해지면 ExitPlanMode 로 승인을 받는다.

[병렬]
- 먼저 상대 세션에 pwd 와 가지를 물어본다. 본 디렉터리에 있으면 병렬을 버리고 한 줄로 친다 —
  훅은 세션이 열릴 때 굳어서, 같은 트리에 세션 둘이 앉으면 서로를 밟는다.
- ListAgents 에는 이름만 뜬다. 사용자가 준 세션 id 가 그 목록에 없다고 죽은 세션이 아니다 —
  이름으로 물어보면 그 세션이 맞다(2026-09-22 실측).
- worktree 를 파는 명령과 그 트리에서 claude 를 띄우는 것은 **다른 일**이다. cd 가 안 먹으면
  둘 다 본 디렉터리에서 돌고, 그러면 본 디렉터리가 B 가지를 물고 세션 둘이 겹친다(2026-09-22 실측).
- 보이면 CLAUDE.md 「병렬 줄」 표대로 가른다. 줄마다 청크 번호 대역과 V 번호를 따로 떼고,
  8080·3000·컴포즈 DB·느린 레인(Testcontainers, verify.sh --full backend)을 쓰는 청크는
  전부 한 줄에 몬다.
- 상대 줄에 보내는 것은 「무엇을 해라」가 아니라 분할표 행 그대로다 —
  축·강제 지점·건드리는 자리·닫힘 넷.
- PROGRESS.md 「현재 상태」 블록은 상대 줄이 안 고친다. 허브 문서는 더하기만 한다.
- 커밋은 git add -A 를 안 쓴다. status 를 보고 경로를 지정한다 — 남의 줄 파일이 딸려 온다.

[실행]
- 청크마다 시작 세 줄(무엇을 닫나 / 걸리는 축 / 강제 지점을 어디에 두나)을 말하고 들어간다.
  계획에 적은 것과 달라지면 그 자리에서 밝힌다.
- 계획에서 고른 결정은 다시 안 묻는다. 계획에 없던 갈림길만 멈춘다.
- 청크 하나 = 커밋 하나. 청크마다 push 하지 않는다.
- 닫기 전에 bash scripts/verify.sh. 못 돌렸으면 못 돌렸다고 밝힌다.
- PLAN 분할표 행과 PROGRESS 이력 한 줄을 청크마다 고친다.
- 청크를 닫을 때마다 「n/10, 남은 것」 한 줄만 보고한다. 계획을 다시 설명하지 않는다.

[막히면]
- 전제가 틀린 것을 발견하면 그 자리에서 범위를 고치고 무엇이 틀렸는지 밝힌다.
  계획에 적힌 대로 치지 않는다.
- 결정이 필요해서 막히면 그 청크를 접고 다음으로 간다. 청크는 서로 독립이라 건너뛸 수 있다.
  접은 것은 PROGRESS 에 무엇을 기다리는지 적는다.
  미완인 작업물은 `wip/<청크>` 곁가지에 커밋하고 작업 가지로 돌아온다 — 빨간 트리가 `work/*` 에 오르면 commit hook 이 막는다(`Q215`).
- 같은 자리에서 두 번 막히면 멈추고 묻는다. 세 번째 시도를 하지 않는다.

[마무리]
- 다섯째 청크를 닫으면 한 번 멈추고, 남은 토큰으로 나머지가 들어가는지 다시 잰다.
  안 들어가면 거기서 /wrapup 하고 PR 을 끊는다.
- 열 개를 다 쳤거나 토큰이 20% 밑으로 떨어지면 거기서 멈추고 /wrapup.
- PR 본문에 청크마다 그 시작 세 줄을 적는다. 리뷰가 「말한 축과 편 축이 같나」를 보는 입력이다.
- 밀기 전 bash scripts/verify.sh --full 은 push 와 따로 낸다. 한 체인으로 묶으면
  PreToolUse 훅이 낡은 도장을 보고 막는다.
- 병렬이었으면 본 디렉터리에서 git merge --no-ff 로 합치고, 검증을 다시 돌리고,
  앞 줄 마지막 이력 행의 커밋 해시를 채운 뒤 PR 을 하나만 연다.

토큰은 이번 5시간 창에 __% 남았다. 주간이 그보다 적으면 __% 다.
```

## 조항마다 무엇을 막나

| 조항 | 빼면 |
|---|---|
| `/warmup` 을 맨 위 한 줄로 | 청크로 바로 들어가서 무엇을 어기는지 모른 채 지나간다 |
| 깨진 것을 계획 1번에 | 빨간 테스트가 나머지 아홉의 검증 신호를 전부 가린다 |
| 설명 모드를 계획 2번에 | 켜 둔 채로 열 개를 잡으면 구조 펴기에 예산이 다 간다 |
| 손 줄·측정값 청크를 뺀다 | 컴포즈를 띄워야 열리는 청크가 계획 중간에서 멈춘다 |
| **입구가 계획 안에 있나** | 아무도 못 채우는 표를 만들고 닫는다. **2026-09-22 에 실제로 그랬다** |
| **결정을 계획 단계에 몬다** | 열 개 중간중간 멈춰서 물어본다. 묶는 값이 사라진다 |
| 번호 대역·`V` 번호 예약 | 「최대+1」로 따다가 두 줄이 같은 번호를 문다(2026-09-21 실측) |
| 상대 세션에 `pwd` 를 묻는다 | 같은 트리에 세션 둘이 앉아 서로를 밟는다. **두 번 엇갈린 자리다**(2026-09-21·22) |
| 분할표 행 그대로 보낸다 | 상대 줄이 축과 닫힘 조건을 모르고 친다 |
| `git add -A` 금지 | 남의 줄 파일이 커밋에 딸려 온다(2026-09-19 실측) |
| **막히면 접고 다음으로** | 열 개 중 하나의 전제가 틀린 자리에서 세션 전체가 선다 |
| 다섯째에서 한 번 잰다 | 열째를 치다 토큰이 끊기면 마무리를 못 하고 끝난다 |
| PR 본문에 시작 세 줄 | 리뷰가 축을 대조할 입력을 못 받는다 |
| `--full` 을 push 와 따로 | push hook 이 막는다 — PreToolUse 라 체인 시점의 도장이 아직 `fast` 다 |
| 토큰 비율을 마지막 줄에 | 안 적으면 규칙상 청크 하나만 치고 멈춘다 |

## 쓸 때 정하는 셋

**토큰은 어느 쪽 수를 적나.** 창과 주간 둘 다 적는다. **묶음 크기를 깎는 것은 작은 쪽**이다 —
주간이 넉넉해도 창이 얕으면 열 개가 한자리에 안 들어가고, 창이 새로 열려도 주간이 바닥이면
그날 켤 묶음이 아니다.

**계획 모드로 드는 말.** `/plan` 슬래시는 이 저장소에 없다. 「계획 모드로 들어간다」는 텍스트나
Shift+Tab 이 실제 입구다.

**PR 을 몇으로 끊나.** 2026-09-21 PR #68 이 여덟 청크였고 리뷰 지적 둘이 **같은 PR 안에서
뒤 청크가 앞 청크 문장을 낡게 만든 것**이었다. 열 개면 그 확률이 는다 — 다섯씩 둘로 끊으면
리뷰 diff 가 작아지는 대신 마무리를 두 번 돈다.

## 처음 돌려 본 실측 (2026-09-22)

열하나를 계획하고 쳤다. 프롬프트가 실제로 값을 한 자리와 못 막은 자리가 갈렸다.

| 무엇 | 결과 |
|---|---|
| **결정을 계획 단계에 몬다** | 값을 했다 — 쿠폰의 전금법 경계와 `R27` 흡수를 미리 정해서 실행 중에 한 번도 안 멈췄다 |
| **묶음에서 뺄 것** | 값을 했다 — 검색 줄(`60`·`61`)이 선행 `D21` 에 막혀 있는 것을 계획에서 걸렀다 |
| **다섯째에서 한 번 잰다** | 값을 했다. 남은 여섯이 들어가는 것을 확인하고 이어 갔다 |
| **병렬** | **두 번 엇갈렸다.** 위 [병렬] 의 셋이 그 실측이다 |
| **못 막은 것** | 「입구는 뒤 청크다」를 세 청크가 적었는데 **그 청크가 계획에 없었다** — 마무리의 셋째 대조가 잡았다. 계획 단계에서 **「이 묶음이 만든 것을 누가 쓰나」**를 한 번 물었으면 먼저 걸렸다 |

**그래서 계획 6번을 그때 넣었다** — 「이 묶음이 세우는 표·권한·문서를 부르는 입구가 계획
안에 있나」. 스키마 청크를 여럿 묶으면 입구가 통째로 빠지는 것이 **기본값**이라, 묶을수록
이 물음이 커진다.
