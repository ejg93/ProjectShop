# 동시성·트랜잭션 규약

같은 자원에 요청이 겹칠 때 무엇을 어떤 방식으로 어떻게 막는지 정한다.

기준은 PostgreSQL 17 문서와 Stripe 멱등 요청이다. 링크는 `external-references.md` 에 있다.

## 격리 수준 — Read Committed 그대로

Postgres 기본값이다. 명시하지 않는다.

Read Committed 에서 한 트랜잭션 안의 같은 조회가 다른 결과를 낼 수 있다.
중간에 다른 트랜잭션이 커밋하면 그것이 보인다.

**그런데 이 프로젝트에서 그게 실제로 문제되는 자리는 재고 차감 하나다.**
아래 방식이 그 자리를 문장 하나로 막으므로 격리 수준을 올릴 이유가 없다.

Repeatable Read 로 올리면 직렬화 실패(`40001`)가 뜨고, 그러면 **모든** 트랜잭션에
재시도 코드가 있어야 한다. 문제 하나를 막으려고 전역 비용을 치르는 셈이다.

## 재고 차감 — 조건부 UPDATE

```sql
select move_stock(:skuId, -:qty, 'order_placed', :orderId)
```

**함수 안이 조건부 UPDATE 다.** 가용 재고가 모자라면 아무것도 안 하고 `false` 를 준다 —
예외로 바꾸면 「재고 부족」이 오류 경로로 올라가서, 부르는 쪽이 정상적인 실패와 진짜 고장을
같은 자리에서 받게 된다.

```sql
update sku_stock
   set on_hand = on_hand + p_quantity
 where sku_id = p_sku_id and available_count >= -p_quantity
```

**재고를 옮기는 입구가 그 함수 하나다**(청크 53). 이력을 같이 남기려고 앱이 두 문장으로 하면
한쪽만 도는 자리가 생기고, `sku_stock.on_hand` 를 직접 고치는 UPDATE 는 트리거가 거부한다 —
관례로 두면 새 경로가 이력을 빼먹고 그 구멍은 숫자가 안 맞는 날에야 드러난다.

**조건이 `on_hand` 이 아니라 `available_count` 다.** 가용 재고는 `on_hand - safety_stock` 을
DB 가 계산해 저장하는 생성 컬럼이라(청크 52), 안전 재고를 앱이 빼지 않는다 —
빼는 자리가 화면·장바구니·주문 셋이면 세 값이 갈린다.

**갱신된 행이 0개면 재고가 모자란 것이다.** 조회해서 검사하고 다시 쓰는 절차가 없다.

### Read Committed 인데 왜 안전한가

읽고 검사하고 쓰는 방식이 위험한 이유는 읽은 값이 쓰기 전에 낡기 때문이다.

```
A: stock 읽음 → 1        B: stock 읽음 → 1
A: 1 >= 1 통과           B: 1 >= 1 통과
A: stock = 0 로 씀       B: stock = 0 로 씀     ← 2개가 팔렸는데 1개만 빠졌다
```

조건부 UPDATE 에는 그 틈이 없다. **Postgres 는 UPDATE 가 잠금을 기다렸다가 풀리면
그 행의 최신 버전을 다시 읽고 `where` 를 다시 평가한다.**

```
A: update 실행, 행 잠금                B: update 실행 → A 를 기다림
A: stock 1 → 0, 커밋                   B: 잠금 풀림 → stock 을 0 으로 다시 읽음
                                       B: 0 >= 1 이 거짓 → 0행 갱신 → 재고 부족
```

낡은 값으로 판단하는 경로 자체가 없다.

### 대가

**왜 실패했는지를 UPDATE 결과만으로는 모른다.** 0행은 재고 부족일 수도 있고
그 `sku` 가 없거나 판매중지일 수도 있다.

0행이 나오면 그때 한 번 조회해서 이유를 가른다. 실패 경로에서만 도는 쿼리다.

## 여러 행을 잠글 때 — id 오름차순

한 주문이 `sku` 를 여럿 차감한다. 잠그는 순서가 요청마다 다르면 데드락이 난다.

```
A: sku 10 잠금 → sku 20 대기
B: sku 20 잠금 → sku 10 대기        ← 서로 기다린다
```

**차감 전에 `sku_id` 를 오름차순으로 정렬한다.** 모두가 같은 순서로 잠그면 순환이 안 생긴다.

주문 항목의 표시 순서와는 무관하다. 정렬은 차감 직전에만 한다.

### 세는 불변식은 부모 행을 잠그고 센다 — 지연 트리거도 예외가 아니다

「대표가 0이 아니다」처럼 **행의 개수**를 지키는 불변식은 제약으로 못 걸어서 트리거가 센다(`Q169`).
지연 트리거는 커밋 직전에 도는데, **두 트랜잭션이 동시에 커밋하면 서로의 삭제를 못 보고 둘 다 통과한다.**
그래서 **세기 전에 부모 행(`seller`)을 `for update` 로 잠근다** — 뒤에 온 쪽이 앞의 커밋을 기다렸다가
새 스냅숏으로 다시 센다. 이것은 Read Committed 가 문장마다 스냅숏을 새로 잡는 성질에 기댄다(위 「격리 수준」).

**앱 검사도 같은 행을 먼저 잠근다.** 그래야 겹친 요청의 뒤쪽이 트리거의 500 이 아니라 앱의 422 를 받는다.
여러 셀러를 잠글 때는 위 규칙대로 `seller_id` 오름차순이다(`requireNotLastOwnerAnywhere`·`check_withdrawal_keeps_owner`).

## 멱등키 — 클라이언트가 만든다

같은 요청이 두 번 도착해도 결과가 하나이게 만든다.
네트워크가 끊겨서 클라이언트가 응답을 못 받은 경우, 요청은 서버에 닿아 처리됐을 수 있다.

### 형식과 전달

| 항목 | 값 |
|---|---|
| 만드는 쪽 | 클라이언트 |
| 형식 | UUIDv4 |
| 전달 | `Idempotency-Key` 요청 헤더 |
| 범위 | 계정별로 유일하다. 남의 키와 겹쳐도 상관없다 |
| 보관 | 24시간. 지나면 지운다 |

주문번호(`D9`)와 다르다. 주문번호는 사람에게 보이는 식별자고, 멱등키는 요청을 가르는 값이다.

**IETF 초안과 대조했다**(2026-09-21, `Q61`). `draft-ietf-httpapi-idempotency-key-header-07` 은
헤더 이름·422·409·재생 넷 중 셋이 우리와 같고 **값의 문법 하나가 갈린다** — §2.1 이
「Item Structured Header(RFC 8941), 값은 String」이라 `Idempotency-Key: "…"` 로 감싸라고 한다.

**우리는 생 문자열을 계속 받는다.** 근거 셋이다.

- 그 초안은 **Expired** 다(2026-04-18 만료). 만료된 I-D 는 표준이 아니라 **관례(4순위)**고 우리 규약이 이긴다
- 큰따옴표를 요구하면 **보내는 쪽이 전부 바뀐다** — 우리 화면과 PG 호출 양쪽이다
- 실물 관례가 생 문자열이다(Stripe). 받는 쪽을 넓히는 것은 언제든 되고 좁히는 것은 안 된다

**초안이 RFC 가 되면 여기를 다시 연다** — 출처가 2순위로 올라가서 판단이 뒤집힌다.
**누가 보나**: 「바깥 근거」 점검이 인용의 판·상태를 다시 읽는 자리다(`/inspection`).

### 어디에 요구하나

| 메서드 | 요구 |
|---|---|
| `POST /api/orders`, `POST /api/payments` | **클라이언트가 만든 키가 필수.** 없으면 400 |
| `POST /api/refunds/{번호}/approve` | **키를 우리가 만든다** — 아래 |
| 그 밖의 `POST` | 안 받는다 |
| `GET`, `PUT`, `DELETE` | 필요 없다. 여러 번 해도 결과가 같다 |

돈이나 재고가 움직이는 `POST` 에만 건다. 전부에 걸면 클라이언트가 의미 없는 키를 만들게 된다.

**환불 승인은 방식이 다르다**(`Q14` 에서 표에 더했다). 돈이 나가는 자리인데 클라이언트 키를
안 받는 이유는 **이미 그 요청을 가리키는 이름이 있어서**다 — 환불번호다.

- PG 를 부를 때 **환불번호를 멱등키로 넘긴다.** 같은 키에 PG 가 같은 답을 준다
- 우리 갱신이 조건부다 — `where refund_number = :번호 and status = 'requested'` 라
  둘째 요청은 0행이고 `REFUND_ALREADY_DECIDED` 로 끝난다

**클라이언트가 키를 만들 이유가 없는 자리**가 이렇게 갈린다 — 주문·결제는 요청이 자원을
만들어서 그 전에는 이름이 없고, 환불 승인은 이미 있는 자원의 상태를 옮긴다.

### 서버가 하는 일

```
키가 처음이다        → 선점하고 처리한다. 끝나면 응답 본문을 저장한다
같은 키가 또 왔다    → 저장된 본문을 그대로 돌려준다
같은 키가 처리 중이다 → 앞 요청이 끝날 때까지 기다린다
                       기다림이 lock_timeout 을 넘기면 409
같은 키인데 본문이   → 422. 키를 재사용한 것이다
서로 다르다
```

본문 비교는 요청 본문의 해시로 한다. 본문 전체를 보관하지 않는다.

### 선점·처리·저장을 한 트랜잭션에 둔다

이게 나머지를 다 정한다. 서블릿 필터에 두면 셋이 갈라져서
**주문은 커밋됐는데 기록은 진행중인 구간**이 생기고, 그 구간에서 서버가 죽으면
재전송이 영원히 409 를 받는다. 타임아웃으로 풀면 이번엔 중복 주문이 다시 열린다.

한 트랜잭션이면 어디서 죽든 전부 롤백이라 **반쪽 상태가 존재하지 않는다.**
구현은 `IdempotencyService` 고, 컨트롤러가 작업을 람다로 넘긴다.

### 바깥 시스템을 부르는 자리는 감싸는 곳이 다르다

**결제가 그 자리다**(청크 12). 위 규칙과 아래 「트랜잭션 경계」가 정면으로 부딪힌다 —
처리를 트랜잭션에 넣으라는 것과 트랜잭션 안에서 바깥을 부르지 말라는 것이 같이 걸린다.

**PG 호출만 밖으로 뺀다.** 순서가 「주문 조회 → PG 호출 → 기록」 이고,
`run()` 이 감싸는 것은 마지막 하나뿐이다.

| | 주문 생성 | 결제 |
|---|---|---|
| 감싸는 곳 | 컨트롤러 | **서비스**(`PaymentService`) |
| 왜 | 컨트롤러가 유일한 입구다 | 컨트롤러가 감싸면 PG 호출이 트랜잭션 안으로 들어간다 |

**밖으로 뺀 대가가 둘이다.**

1. **중복 승인을 우리가 못 막는다.** 재전송이 PG 를 두 번 부르는 구간이 열린다.
   그 구간은 **PG 가 같은 멱등키에 같은 결과를 주는 것**으로 닫는다 — 우리 키를 그대로 넘긴다.
   실물 PG(Stripe·Toss)가 멱등키를 받는 이유가 이것이고, 모의 PG 도 같은 계약을 구현한다
2. **재생 확인도 같이 나와야 한다.** 재전송 시점에는 그 주문이 이미 `paid` 라
   주문 상태 검사가 **재생에 닿기 전에** 막는다. 그래서 `replayIfPresent` 로 먼저 보고,
   있으면 그것을 돌려준다. 없을 때만 상태를 보고 PG 를 부른다

### 거절은 저장한다

아래 「실패는 저장하지 않는다」와 다른 것이다. **예외로 깨진 요청**과 **거절이라는 결과**가 갈린다.

카드 거절은 자원(`payment` 행)이 생기고 주문이 `payment_failed` 로 가며 재고가 돌아온다(`D7`).
막을 중복이 있으므로 저장한다. 예외로 던지면 그 셋이 전부 롤백돼서
**`D7` 이 정한 `payment_failed` 가 배치 말고는 아무 데서도 안 쓰인다.**

### 409 는 "진행중" 이 아니라 "너무 오래 기다렸다" 다

한 트랜잭션이라 **처리 중인 행은 다른 요청에 안 보인다.** 커밋 전이기 때문이다.
대신 같은 키의 뒤 요청은 유니크 충돌로 대기하고, 앞이 커밋되면 재생을 읽고
롤백되면 자기가 처리한다 — **대기가 알아서 옳은 답을 낸다.**

앞 요청이 길면 뒤가 그만큼 붙잡히므로 `lock_timeout` 으로 끊고 그때만 409 를 준다.

### 실패는 저장하지 않는다

예외가 나면 멱등 기록도 같이 롤백된다. 저장하려면 트랜잭션을 쪼개야 하는데
그건 위에 적은 반쪽 상태를 그대로 불러온다.

**실패는 자원이 안 생기므로 막을 중복이 없다.** 재고 부족·검증 실패는 아래
「재시도하지 않는다」 목록에 있는 것들이라 재전송해도 같은 결과가 나온다.

### 감싸는 것을 빠뜨리면 무엇이 잡나

멱등이 필요한 경로가 실제로 `IdempotencyService` 를 거치는지는 **테스트가 지킨다.**

필터로 헤더만 강제하는 방법도 저울질했다. 그런데 필터는 `run()` 이 실제로 불렸는지 모르므로
**"헤더는 요구하는데 멱등은 안 걸린" 상태**를 만들 수 있고, 그건 아예 없는 것보다 나쁘다 —
클라이언트가 키를 성실히 보내고 문서에도 필수라고 적혀 있는데 안 걸린다.

## 재시도 — 다시 해서 달라지는 것만 3회

| 재시도한다 | 무엇으로 가르나 |
|---|---|
| 직렬화 실패 | SQLSTATE `40001` |
| 데드락 | SQLSTATE `40P01` |
| **결제사 무응답** | 예외 타입(`MockPaymentGateway.TimedOut`). DB 예외가 아니라 SQLSTATE 로 안 갈린다 |
| **노출 번호 충돌** | 예외 타입(`ExposedNumber.Conflict`, `Q49`). **SQLSTATE 로 안 갈린다** — `23505` 는 다시 해도 같은 유일 위반과 구분이 안 된다 |

간격은 50ms, 100ms, 200ms 다. 3회에도 안 되면 실패로 떨어뜨린다.

**결제사 무응답에서 키를 새로 만들지 않는다.** 같은 키로 다시 부르는 것이 재시도고,
키를 바꾸면 PG 가 다른 요청으로 보고 **두 번 승인한다.** 3회를 다 쓰면 504 다(`ErrorCode`) —
승인이 났는지 우리가 모르는 상태라 주문은 그대로 두고, 같은 키로 다시 오면 PG 가 그때 답한다.

Read Committed 에서 `40001` 은 거의 안 뜬다. 그래도 넣어 두는 이유는
나중에 격리 수준을 올리는 자리가 생겨도 재시도 자리를 다시 안 만들려는 것이다.

| 재시도하지 않는다 | 왜 |
|---|---|
| 재고 부족 | 다시 해도 같다 |
| 권한 없음 | 다시 해도 같다 |
| 검증 실패 | 다시 해도 같다 |
| 멱등키 충돌 | 재시도가 아니라 중복이다 |

**재시도는 트랜잭션 바깥에서 건다.** 안쪽에서 걸면 이미 깨진 트랜잭션을 붙들고 다시 돌린다.
Postgres 가 그 트랜잭션을 abort 시켜서 다음 문장이 `25P02` 로 죽는다 — **안쪽은 성공할 수 없는 자리**다.

### 어디에 걸려 있나

`Retries.onConflict` 이 그 자리다(청크 10c). **예외 타입이 아니라 SQLSTATE 로 가른다** —
Postgres 의 데드락은 `DeadlockLoserDataAccessException` 이 아니라 상위 타입으로 온다(`stack.md`).

**무엇을 다시 돌릴지는 부르는 쪽이 정한다**(청크 12). `Retries.on` 이 판정을 받고
`onConflict` 은 그 위에 SQLSTATE 판정을 얹은 것이다 — 간격과 횟수가 한 군데뿐이라
자리마다 다른 값이 생기지 않는다.

| 자리 | 왜 여기가 바깥인가 |
|---|---|
| `OrderController.create` | `IdempotencyService.run` 이 트랜잭션 경계다. 그걸 통째로 감싼다 |
| `OrderStatusBatch.move` | 건마다 트랜잭션이 갈려 있어서 이 자리가 이미 바깥이다 |
| `PaymentService.pay` | 기록 트랜잭션을 감싼다. **PG 호출 재시도는 그보다 더 바깥**이라 따로 돈다 |
| `RefundController.request` | 환불번호를 뽑는 자리가 `RefundService.request` 안이고 그것이 `@Transactional` 이다(`Q49`) |
| `InquiryController.create` | 문의번호가 같은 모양이다(`Q49`) |
| `SettlementService.insertStatement` | **안 감싼다.** 배치 안이라 `RetryableBatch` 가 10분 뒤 다시 돈다 |

**노출 번호는 뽑는 자리가 아니라 부르는 자리에서 다시 돈다**(`Q49`). `ExposedNumber` 안에 재시도 루프가
있었는데 호출 다섯이 전부 `@Transactional` 안이라 **한 번도 못 돌았다** — 두 번째 `insert` 가
`DuplicateKeyException` 이 아니라 `25P02` 로 와서 잡히지도 않고 500 이 됐다. 재시도 3회가 장식이었다.

**제약 이름을 부르는 자리가 든다.** `ExposedNumber.insert` 에 그 번호를 지키는 유일 제약 이름을 넘기고,
그 제약이 걸렸을 때만 `Conflict` 로 바꾼다. **이름 꼬리(`_number_unique`)로 안 가른다** —
결제사가 준 승인번호·환불번호가 같은 꼬리를 쓰는데 **바깥에서 받은 값은 다시 뽑을 수가 없다.**
넘긴 이름이 실재하는지는 `ExposedNumberConstraintTest` 가 센다.

**멱등키보다 바깥이다.** 안쪽이면 선점 기록을 남긴 채로 다시 돌게 되는데, 애초에 그럴 수 없다 —
깨진 트랜잭션이라 그 기록도 같이 롤백된다. 롤백됐으니 같은 키로 다시 들어오는 것이 맞고,
앞 시도가 아무것도 안 남겼으므로 **막을 중복이 없다.**

## 판정 캐시 무효화 — 지금은 프로세스 안이다

**캐시가 인스턴스마다 하나씩이다**(`PermissionCacheConfig`, Caffeine). 그래서 역할을 회수하면
**그 요청을 받은 인스턴스만** 지우고 나머지는 TTL(60초)이 끝날 때까지 옛 규칙을 쓴다.
**한 대로 도는 동안은 안 보이다가 늘리는 순간 조용히 틀리는 자리**고, 늘리기 전에 옮겨야 한다.

| 무엇 | 지금 |
|---|---|
| 어디에 | 프로세스 안(Caffeine). 상한 10,000 · TTL 60초 |
| 무효화 | `PermissionRuleLoader.evict` 가 이 인스턴스의 셋을 지운다 |
| 안전망 | TTL. **무효화를 빠뜨렸을 때**와 **다른 인스턴스**를 둘 다 이것이 자른다 |
| 즉시여야 하는 것 | 탈퇴·차단은 캐시가 아니라 **세션을 끊는 쪽**이 든다(`ADR 0010`) |

**옮기는 것은 `39` 고, 2026-09-21 에 한 번 치다가 되돌렸다.** Redis 로 바꾸니 규칙 캐시가
**한 번도 안 차는데 아무 신호가 없었다** — 강등 핸들러가 그 실패를 삼켜서 「도는 척」이 됐다.
값 직렬화를 JSON·JDK 둘 다 대 봐도 같은 자리가 남아서, **원인을 밝히기 전에는 안 옮긴다**:
옛 판정이 남는 것보다 **캐시가 없는 편이 덜 위험하다**(있는데 안 도는 것은 성능만 잃지만,
반쯤 도는 것은 판정을 흔든다). 무엇을 실측했는지는 그 행이 든다.

## 트랜잭션 경계

| 규칙 | 왜 |
|---|---|
| 트랜잭션 안에서 외부 호출을 안 한다 | 응답을 기다리는 동안 잠금이 유지된다 |
| 읽기 전용 조회에 트랜잭션을 안 건다 | 커넥션을 오래 쥔다 |
| 한 트랜잭션은 한 유스케이스다 | 여러 유스케이스를 묶으면 잠금 구간이 길어진다 |

**앞의 둘은 `ArchitectureTest` 가 막는다**(`Q32`). 바깥 호출은 `@Transactional` 메서드에서 출발하는 **호출 사슬 전체**를 걷는다 —
람다·private 헬퍼 뒤에 있어도 걸린다. **`REQUIRES_NEW`·`NOT_SUPPORTED` 는 예외가 아니다** — 바깥 트랜잭션을 중단할 뿐 닫지 않아서
커넥션과 잠금이 그대로다. 규칙은 지나온 경계를 메시지에 적기만 한다. 못 보는 것은 `TransactionTemplate` 블록(`NotificationService` 하나)과
인터페이스 뒤 구현체다. 셋째(한 유스케이스)는 여전히 사람이 든다.

결제(청크 12)는 모의 PG 를 호출한다. 호출은 트랜잭션 밖에서 하고,
결과를 받은 뒤 짧은 트랜잭션으로 기록한다. **그 트랜잭션이 멱등 트랜잭션이다** —
위 「바깥 시스템을 부르는 자리는 감싸는 곳이 다르다」가 그 배치를 정했다.

안 지키면 무슨 일이 나는지가 여기서는 구체적이다. PG 응답을 기다리는 동안
멱등키 행의 락이 유지되므로 **느린 PG 하나가 같은 키의 뒤 요청을 전부 409 로 만든다**
(`lock_timeout` 3초).
