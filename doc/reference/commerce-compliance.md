# 전자상거래 법·정책 요건표

멀티 셀러 쇼핑몰에 걸리는 법 요건을 조문 단위로 적고, 각 요건이 이 프로젝트의 어느 스키마·API·화면에 걸리는지 매핑한다.

## 이 문서의 성격

법률 자문이 아니다. 이 프로젝트는 로컬 전용이라 실제 준수 의무의 대상이 아니다.
요건이 설계의 어느 지점을 건드리는지를 근거로 남기려고 쓴다.

조문 번호와 기간은 2026년 8월 기준의 정리이고 **검증을 안 거쳤다.** 법은 개정되고 조문 번호는 밀린다.
실제 서비스에 쓸 거면 국가법령정보센터(law.go.kr)에서 원문을 다시 확인해야 한다.
확인 안 된 수치를 확정된 것처럼 쓰면 이 문서를 두는 의미가 없어진다.

법률 약칭은 아래와 같이 쓴다.

| 약칭 | 정식 명칭 |
|---|---|
| 전자상거래법 | 전자상거래 등에서의 소비자보호에 관한 법률 |
| 개인정보법 | 개인정보 보호법 |
| 정보통신망법 | 정보통신망 이용촉진 및 정보보호 등에 관한 법률 |
| 표시광고법 | 표시·광고의 공정화에 관한 법률 |

## R1. 셀러 신원 정보 표시

통신판매업자는 상호, 대표자 성명, 주소, 전화번호, 전자우편주소, 사업자등록번호, 통신판매업 신고번호를 표시한다.
사이버몰 초기화면 표시가 원칙이고, 마켓플레이스에서는 **셀러마다** 이 정보가 다르다.

지금 `seller` 테이블은 `code`·`name`·`status` 뿐이라 표시할 것이 없다. 청크 3c에서 컬럼을 채운다.

| 컬럼 | 담을 것 | 비고 |
|---|---|---|
| `business_name` | 상호 | `name` 은 표시용 이름이라 법정 상호와 다를 수 있다 |
| `representative_name` | 대표자 성명 | |
| `business_reg_no` | 사업자등록번호 | 10자리, 검증 규칙이 있다 |
| `mail_order_no` | 통신판매업 신고번호 | `2026-서울강남-01234` 형식 |
| `address` | 사업장 주소 | |
| `phone` | 전화번호 | |
| `email` | 전자우편주소 | |

상품 상세 화면(14)이 그 상품을 파는 셀러의 정보를 끌어다 표시한다.
상품이 `seller` 를 가리키므로 조인 한 번이면 되지만, **상품 목록에서도 필요한지**는 화면 설계에서 정한다.

## R2. 중개자 지위 고지

마켓플레이스 운영자는 자신이 통신판매의 당사자가 아니라는 사실을 고지한다.
안 하면 셀러의 고의·과실로 생긴 소비자 손해에 연대책임을 진다.

이 프로젝트는 멀티 셀러라 여기에 정면으로 걸린다. 걸리는 자리가 셋이다.

- 주문서와 상품 상세에 "○○는 통신판매중개자이며 통신판매의 당사자가 아니다" 고지
- 이용약관에 같은 내용
- 소비자 요청 시 셀러 정보를 제공할 수 있어야 한다 — R1 데이터가 그대로 쓰인다

## R3. 청약철회 기간과 기산점

단순 변심은 **7일**이다. 기산점이 두 갈래다.

- 계약 내용에 관한 서면을 받은 날
- 재화를 공급받은 날 (서면을 나중에 받았거나 재화가 나중에 온 경우)

광고 내용과 다른 재화면 **공급받은 날부터 3개월 이내, 그 사실을 안 날부터 30일 이내** 중 빠른 쪽이다.

### 설계에 걸리는 지점

청약철회는 상태 전이인데 **기간 조건이 붙은 전이**다. 지금 상태머신에 그런 전이가 없다.

```
배송완료 ──(완료 시각 + 7일 이내)──> 반품요청
         └(7일 지남)──────────────> 전이 거부
```

그래서 `order` 에 배송완료 시각이 필요하다. 상태만 갖고 있으면 기간을 못 잰다.
상태 변경 이력 테이블을 두는 편이 낫다 — 나중에 "언제 배송완료됐나"를 묻는 요건이 또 나온다.

이건 청크 11의 전이표에 조건 컬럼이 생긴다는 뜻이고, 청크 11a(상태 조건부 권한)와 만난다.
**역할이 아니라 시간이 권한을 깎는 사례**라 판정 엔진의 입력에 시각이 들어간다.

## R4. 청약철회 제한 사유

전부 철회되는 건 아니다. 제한 사유가 있다.

- 소비자의 책임으로 재화가 멸실·훼손된 경우
- 소비자의 사용 또는 일부 소비로 가치가 뚜렷하게 감소한 경우
- 시간이 지나 재판매가 곤란할 정도로 가치가 뚜렷하게 감소한 경우
- 복제가 가능한 재화의 포장을 훼손한 경우
- 주문에 따라 개별 생산되는 재화 등, 철회를 인정하면 판매자에게 회복할 수 없는 피해가 예상되는 경우

앞의 셋은 상품 상태 판단이라 시스템이 자동으로 못 정한다. **뒤의 둘은 상품 속성**이라 데이터로 표현된다.

`product` 에 청약철회 제한 여부와 사유를 두고, 제한 상품은 전이 자체를 막는다.
제한 사유가 있는 상품은 **주문 전에** 소비자에게 알려야 해서 상품 상세 화면에도 나온다.

## R5. 환급 기한

청약철회를 받으면 **3영업일** 이내에 대금을 환급한다. 늦으면 지연이자가 붙는다.

모의 결제라 실제 환급은 없지만, 환불 워크플로(12a)에 기한 개념이 들어간다.
요청과 승인을 가르는 설계에서 **승인이 늦어지면 기한을 넘긴다**는 점이 드러나야 한다.

## R6. 거래기록 보존

사업자는 거래기록을 일정 기간 보존한다. 기간이 종류마다 다르다.

| 기록 | 기간 |
|---|---|
| 표시·광고에 관한 기록 | 6개월 |
| 계약 또는 청약철회 등에 관한 기록 | 5년 |
| 대금결제 및 재화등의 공급에 관한 기록 | 5년 |
| 소비자의 불만 또는 분쟁처리에 관한 기록 | 3년 |

### 설계에 걸리는 지점

주문·결제 행을 지우면 안 된다. `DELETE` 를 막고 `deleted_at` 같은 표시로 가린다.

여기서 R9(개인정보 파기)와 **정면으로 부딪친다.** 개인정보는 목적을 달성하면 지워야 하는데,
거래기록은 5년을 갖고 있어야 한다. 둘 다 만족하려면 **한 테이블을 두 층으로 갈라야 한다.**

- 거래 사실(금액, 상품명, 일시, 상태) — 5년 보존
- 개인 식별 정보(이름, 주소, 연락처) — 파기 대상

주문 항목에 상품명과 가격을 복사해 박제하기로 한 결정(PLAN.md)이 여기서 한 번 더 값을 한다.
`sku` 를 지워도 주문 기록은 남는다.

배송지 주소는 주문에 복사해 넣는데 그게 개인정보라 파기 대상이다.
**주문 테이블에서 개인정보 컬럼만 따로 뺄지**를 청크 10a에서 정한다.

## R7. 개인정보 수집 동의

수집·이용에는 동의가 필요하고, 필수 동의와 선택 동의를 구분해서 받는다.
선택 동의를 거부해도 서비스는 제공해야 한다.

동의는 받은 사실을 입증해야 하므로 **동의 이력 테이블**이 필요하다. 계정 테이블의 불린 컬럼으로는 부족하다.
동의 시점, 동의 항목, 동의 여부, 철회 시점이 남아야 한다.

### 동의받을 때 알려야 하는 것

제15조제2항이 넷을 요구한다. 이걸 알리고 나서 받은 동의라야 동의다.

| 알릴 것 | 예 |
|---|---|
| 수집·이용 목적 | 회원 식별과 주문 처리 |
| 수집 항목 | 이메일, 이름, 접속 IP |
| 보유·이용 기간 | 탈퇴 후 30일 |
| 거부할 권리와 불이익 | 필수 항목을 거부하면 가입이 안 된다 |

**입증 대상은 항목 이름이 아니라 이 내용이다.** "마케팅 수신에 동의했다" 만으로는 부족하고,
그때 무엇을 알리고 받았는지가 남아야 한다.

`consent_item` 에 개정판(`version`)을 둔 이유가 여기 걸린다 — **판을 가리키는데 판의 내용이 없으면
가리킬 것이 없다.** 지금 스키마는 `title` 뿐이라 이 요건을 못 만족한다. 청크 `5j` 가 채운다.

## R8. 셀러에게 주문자 정보 제공

마켓플레이스에서 셀러가 주문자 이름·연락처·주소를 보는 건 **제3자 제공**이다.
운영자와 셀러는 별개 사업자라 내부 이용이 아니다.

이게 권한 스코프와 만나는 자리다. `scope=seller` 로 주문을 조회할 때 **어떤 컬럼까지 보이는가**가 정해져야 한다.
행 단위 권한만으로는 부족하고 컬럼 단위 판단이 붙는다.

- 배송에 필요한 항목만 — 수령인, 연락처, 주소
- 결제 수단 정보는 셀러가 볼 이유가 없다
- 배송이 끝난 뒤에도 계속 보여야 하는지는 별도 판단이다

지금 권한 모델은 `resource + action` 이라 컬럼 단위를 표현할 방법이 없다.
청크 4에서 판정 엔진을 짤 때 **응답 필드를 깎는 층**을 둘지 정한다. 안 두면 셀러가 주문 전체를 본다.

## R9. 개인정보 파기

보유기간이 지나거나 목적을 달성하면 지체 없이 파기한다. 시행령은 정당한 사유가 없으면 5일 이내로 본다.

다른 법령에 따라 보존해야 하는 정보는 **분리 보관**한다. R6이 그 경우다.

### 폐지된 것

1년 미접속 계정의 개인정보를 파기·분리보관하던 유효기간제는 2023년 개정으로 **폐지됐다.**
오래된 자료에 이 규칙이 남아 있으니 그대로 베끼면 안 된다.

### 설계에 걸리는 지점

`app_user.status = 'withdrawn'` 은 이미 있지만 파기 규칙이 없다.
탈퇴가 곧 삭제가 아니라는 게 핵심이다.

| 대상 | 처리 |
|---|---|
| 계정 식별 정보 | 파기 또는 비식별화 |
| 주문 기록 | 5년 보존 (R6) |
| 재가입 방지용 정보 | 별도 근거가 필요하다 |

이메일을 파기하면 `app_user_email_key` 유니크 인덱스와 충돌한다.
`user_2831@deleted.invalid` 같은 값으로 덮을지, 컬럼을 `null` 로 두고 인덱스를 부분 인덱스로 바꿀지 청크 10a에서 정한다.

## R10. 비밀번호 일방향 암호화

비밀번호는 복호화되지 않는 방식으로 저장한다. 안전성 확보조치 기준 고시가 세부를 정한다.

청크 5에서 BCrypt 또는 Argon2를 고른다. Spring Security의 `PasswordEncoder` 가 둘 다 지원한다.
`app_user.password_hash` 컬럼은 이미 있고 알고리즘만 정하면 된다.

해시 알고리즘은 바뀐다. 저장 형식에 알고리즘 식별자가 들어가는 방식(`{bcrypt}$2a$...`)을 써서
나중에 갈아탈 때 기존 계정이 안 깨지게 한다. `DelegatingPasswordEncoder` 가 이걸 한다.

## R11. 처리방침 공개

개인정보 처리방침을 수립하고 공개한다. 이용자가 쉽게 확인할 수 있어야 한다.

청크 13a에서 문안을 쓴다. 실제 서비스 문안이 아니라 **이 프로젝트가 실제로 무슨 데이터를 어떻게 다루는지**를 적는다.
스키마에 없는 항목을 처리방침에 적으면 문서와 코드가 어긋난다.

## R12. 판매가격 표시

소비자에게 최종 지불 가격을 표시한다. 부가가치세를 포함한 금액이다.

`sku.price` 가 무엇을 담는지 정의가 필요하다. 부가세 포함 판매가로 두는 편이 단순하다.
공급가액과 세액이 따로 필요해지는 건 세금계산서·정산 단계이고, 그때 역산한다.

배송비를 상품 가격과 어떻게 합쳐 보여줄지도 여기 걸린다. 멀티 셀러라 **셀러별로 배송비가 따로 붙는다.**
장바구니에 두 셀러의 상품이 담기면 배송비가 둘이다. 청크 9·10에서 이 구조가 드러난다.

## R13. 미성년자 거래 취소권

미성년자가 법정대리인의 동의 없이 한 법률행위는 취소할 수 있다.

취소 주체가 미성년자 본인 또는 법정대리인이라, **주문한 사람이 아닌 제3자가 취소를 요청**하는 경로가 생긴다.
지금 권한 모델은 "자기 주문만"(`scope=own`)이라 이 경로를 표현할 방법이 없다.

실제로 다루려면 계정에 생년월일과 법정대리인 관계가 필요하다.
이 프로젝트에서 어디까지 갈지는 청크 11a에서 정한다. 안 다루기로 해도 **왜 안 다루는지**는 적어 둔다.

## R14. 광고성 정보 수신 동의

영리 목적 광고성 정보를 전송하려면 사전 동의를 받는다.
21시부터 다음날 08시까지 전송하려면 별도 동의가 필요하다.

R7의 동의 이력 테이블에 항목으로 들어간다. 야간 수신 동의가 **별개 항목**이라는 점이 설계 포인트다.
불린 하나로 두면 나중에 못 쪼갠다.

## R15. 부당 표시·광고 금지

거짓·과장, 기만적 표시광고를 금지한다.

시스템이 자동으로 판단할 수 없다. 대신 **셀러가 쓴 상품 설명을 운영자가 검수하는 경로**가 있느냐의 문제로 바뀐다.
상품에 검수 상태를 두면 `product` 에 상태 컬럼이 생기고, 검수 권한이 관리자 역할에 붙는다.

이건 권한 축이라 이 프로젝트 주제와 맞다. 다만 청크 6·7 범위를 넘으므로 후보로만 남긴다.

## 이 프로젝트가 안 다루는 것

범위 밖이라 안 하는 것들이다. 안 하기로 했다는 사실 자체가 기록이다.

| 요건 | 왜 안 하나 |
|---|---|
| 소비자피해보상보험·에스크로 | 실제 결제가 없다. 전자상거래법 제24조 |
| 전자금융거래법상 PG 등록 | 모의 결제 모듈이다 |
| 통신판매업 신고 | 실제 사업자가 아니다 |
| 본인확인·실명확인 | 본인확인기관 연동이 필요하다 |
| 세금계산서·현금영수증 | 국세청 연동이 필요하다 |
| 청소년유해매체물 | 취급 상품에 해당 없다 |
