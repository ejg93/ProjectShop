# 금액·통화 규약

금액을 어떻게 저장하고 언제 자르는지 정한다. 정산(청크 17~21)의 1원 오차가 여기서 갈린다.

## 통화

**원화만 쓴다.** 금액 컬럼에 통화 코드를 붙이지 않는다.

다중 통화를 안 하기로 했으므로(`business-model.md`) 통화 컬럼은 값이 하나뿐인 컬럼이 된다.
나중에 필요해지면 그때 컬럼을 추가한다. 지금 넣으면 모든 쿼리에 `and currency = 'KRW'` 가 붙는다.

Money 패턴(Fowler)이 지적하는 두 문제 중 **통화 혼동은 우리에게 안 온다.** 반올림 오차는 온다.

## 저장

금액은 **원 단위 정수**로 저장한다. 타입은 `bigint`.

```sql
total_amount bigint not null
```

원화의 최소 단위가 원이라 소수가 필요 없다.
`numeric` 이나 `decimal` 을 쓰면 소수점 이하가 들어갈 여지가 생기고, 그 값이 어디서 들어왔는지 추적이 어려워진다.

`double` 은 쓰지 않는다. 부동소수점은 `0.1 + 0.2 != 0.3` 이라 돈에 쓰면 안 된다.

JSON 으로 나갈 때도 정수다. 문자열로 감싸는 방식(정밀도 손실 방지)은 원화에 해당이 없다.

### 요율

요율은 **만분율 정수**로 저장한다. 컬럼 이름은 `_bp` 로 끝나고 `1000` 이 `10.00%` 다.

```sql
commission_bp int not null default 1000
```

요율을 `numeric` 으로 두면 금액을 곱한 결과가 소수가 되고, **어디서 자를지를 사람이 관리하게 된다.**
만분율 정수면 아래 절사 규칙이 연산 자체에 들어간다.

```
수수료 = 금액 * commission_bp / 10000     -- 정수 나눗셈이 곧 버림이다
```

주문 항목에 요율을 박제할 때(청크 10)도 정수라 비교가 어긋나지 않는다.
`BigDecimal` 은 `0.10` 과 `0.1000` 이 같지 않아서 박제 값 대조에 함정이 있다.

**화면과 API 는 만분율을 그대로 보여주지 않는다.** `1000` 을 `10%` 로 바꿔서 내보낸다.

## 부가세

`sku.price_incl_vat` 는 **부가세를 포함한 판매가**다. ADR 0007 에서 정했다.
주문에 굳는 `order_item.unit_price_incl_vat` 도 같은 값이라 이름이 같은 꼬리를 단다.

**그 사실이 이름에 들어 있다**(`D2-2`). 값만 봐서는 세금이 포함됐는지 알 방법이 없어
`check` 로 못 막는다 — 공급가액을 넣으려던 사람이 멈추는 자리가 이름뿐이라
강제 지점을 주석에서 이름으로 올렸다(`D23` 축 2).

공급가액과 세액을 따로 저장하지 않는다. 필요할 때 역산한다.

```
판매가 15,000원
공급가액 = 15,000 / 1.1 = 13,636.36... → 13,636
세액     = 15,000 - 13,636 = 1,364
```

세액을 저장하면 부가세율이 바뀔 때 과거 값이 굳는다. 값이 하나여야 어긋나지 않는다.

역산할 때도 **원 미만은 버린다.** 아래 절사 규칙과 같다.

## 절사

### 방식 — 버림

원 미만은 무조건 버린다. 반올림하지 않는다.

부가세 실무에서 원 단위 미만 절사가 관행이고, 법으로 정해진 규정이 없어 각자 정한다.
버림을 고른 이유는 **결과가 한 방향으로만 어긋나서** 검증이 쉽기 때문이다.
반올림은 값에 따라 위아래로 갈려서 합계가 어디서 어긋났는지 찾기 어렵다.

### 예외 — 물어 주는 돈은 올린다

**버림은 우리가 받는 돈의 규칙이다.** 수수료·부가세가 그렇다 — 자를수록 우리 몫이 준다.

**우리가 늦어서 물어 주는 돈은 방향이 반대다.** 지연배상금(`12a-4`, 시행령 제21조의3)이 그 자리고,
버리면 **법이 정한 금액보다 적게 준다.** 원 미만을 올린다.

| 어느 쪽 돈이냐 | 자르는 방향 | 예 |
|---|---|---|
| 우리가 받는다 | 버림 | 수수료, 부가세 역산 |
| 우리가 물어 준다 | **올림** | 환급 지연배상금 |

**규칙이 둘이 아니라 하나다** — 둘 다 **우리에게 불리한 쪽**으로 자른다.
방향을 그렇게 잡으면 어느 자리에서든 「어느 쪽이었더라」를 안 묻는다.

### 단계 — 주문 항목별

수수료는 **주문 항목마다 계산하고 그때 자른다.** 합산한 뒤에 자르지 않는다.

```
항목 A  33,335 × 10% = 3,333.5 → 3,333
항목 B  33,335 × 10% = 3,333.5 → 3,333
항목 C  33,335 × 10% = 3,333.5 → 3,333
                            합계 9,999

전체에서 자르면
        100,005 × 10% = 10,000.5 → 10,000
```

두 방식이 1원 차이가 난다. 항목별을 고른 이유는 **부분 환불** 때문이다.

항목 A 만 환불한다고 하자.

| 방식 | 돌려줄 수수료 |
|---|---|
| 항목별 절사 | 3,333원. **이미 확정돼 있다** |
| 전체 절사 | 10,000원 중 A 의 몫을 다시 나눠야 한다. 나눈 합이 10,000이 안 되면 1원이 뜬다 |

항목별로 잘라 두면 각 항목의 수수료가 처음부터 값으로 존재해서, 환불이 뺄셈 하나로 끝난다.

`business-model.md` 가 "주문 항목에 요율과 수수료액을 둘 다 넣는다" 고 정한 것이 이 규칙과 맞물린다.
요율만 저장하면 절사 규칙이 바뀔 때 과거 수수료가 달라진다.

### 어디에 적용되나

| 계산 | 절사 단위 |
|---|---|
| 수수료 | 주문 항목마다 |
| 부가세 역산 | 계산하는 그 금액마다 |
| 할인·쿠폰 (청크 49~51) | 적용 대상마다. 그때 다시 정한다 |

## 합계의 규칙

**항목의 합이 주문 총액이다.** 주문 총액을 따로 계산하지 않는다.

```
order.total_amount = sum(order_item.amount)
order.commission_total = sum(order_item.commission_amount)
```

총액을 독립적으로 계산하면 항목 합과 어긋날 수 있고, 어긋나면 어느 쪽이 맞는지 판단할 근거가 없다.

**저장한다.** 청크 17-1 에서 정했고 근거와 강제 방식은 `money-invariants.md` 에 있다.
저장하면 빠르고 계산하면 어긋날 수 없는데, 어긋나는 쪽을 지연 트리거로 막는 것을 골랐다.

## 배송비

배송비는 상품 금액과 **따로 둔다.** 수수료를 안 매기므로(`business-model.md`) 합쳐 두면 수수료 계산에서 다시 빼야 한다.

멀티 셀러라 주문 하나에 배송비가 여럿이다. 셀러별로 붙는다.

## 음수

정산 지급액은 음수가 될 수 있다. 정산 후 환불이 나면 이미 준 돈을 회수하기 때문이다.

금액 컬럼에 `check (amount >= 0)` 을 거는 것은 **자원마다 판단한다.**
상품 가격은 음수가 될 수 없지만 정산 잔액은 될 수 있다.

## 이 문서를 고칠 때

절사 규칙을 바꾸면 **이미 계산된 금액은 안 바뀐다.** 주문 항목에 수수료액이 값으로 박혀 있어서다.
그래서 규칙을 바꿔도 과거 정산이 흔들리지 않는다. 이것이 박제의 이유다.

새 계산이 생기면(할인, 포인트, 쿠폰) 절사 단위를 여기에 추가한다.
적지 않으면 개발자마다 다르게 자르고, 합계가 1원씩 안 맞는 자리가 생긴다.
