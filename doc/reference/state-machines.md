# 상태머신 카탈로그

자원마다 어떤 상태가 있고 누가 그것을 옮기는지 정한다.

**전이표 자체는 코드에 선언한다.** ADR 0009 가 정했다. 이 문서는 상태 목록과 전이 주체와 자동 전이다.

## 주문은 두 층이다

**한 주문에 셀러가 여럿일 수 있다.** 셀러 A 는 배송을 끝냈고 B 는 준비 중인 상황이 성립한다.
상태를 한 군데만 두면 이걸 표현할 수 없다.

```
order                        결제가 여기 붙는다
 ├ seller_order  (셀러 A)    배송·취소·반품이 여기 붙는다
 │   └ order_item
 └ seller_order  (셀러 B)
     └ order_item
```

| 층 | 무엇을 담나 | 왜 여기인가 |
|---|---|---|
| `order` | 결제 | 고객은 한 번 결제한다. 셀러별로 나눠 결제하지 않는다 |
| `seller_order` | 배송·취소·반품 | 셀러마다 따로 굴러간다. 배송비도 셀러별로 붙는다 |

**셀러 권한이 이 경계와 그대로 맞아떨어진다.** `scope=seller` 가 `seller_order` 를 자른다.
셀러가 남의 배송 정보를 볼 경로가 구조에서 사라진다.

주문 항목(`order_item`)에는 상태를 안 둔다. 항목 단위 부분 취소는 하지 않는다.
취소·반품의 최소 단위는 `seller_order` 다.

## `order` 상태 — 결제

| 상태 | 뜻 |
|---|---|
| `payment_pending` | 주문이 만들어졌고 재고를 잡았다. 결제를 기다린다 |
| `paid` | 결제가 끝났다 |
| `payment_expired` | 30분 안에 결제가 안 끝나 재고를 되돌렸다 |
| `payment_failed` | 결제가 거절됐다 |

### 재고는 결제 전에 잡는다

`payment_pending` 을 두는 이유다. 주문서를 띄워 둔 사이에 남이 채가는 것을 막는다.

```
주문 생성 → 재고 차감 → payment_pending
  결제 성공  → paid
  30분 초과  → payment_expired + 재고 복구
```

결제가 성공해야 주문을 만드는 방식도 있었다. 상태가 줄지만
**결제를 마치고 재고를 깎으려는 순간 품절이면 즉시 환불해야 한다.**
무통장입금 같은 지연 결제도 못 붙인다.

## `seller_order` 상태 — 배송

| 상태 | 뜻 |
|---|---|
| `preparing` | 셀러가 상품을 준비한다 |
| `shipping` | 배송이 시작됐다 |
| `delivered` | 배송이 끝났다. 청약철회 기간이 여기서 시작된다 |
| `confirmed` | 구매가 확정됐다. 정산 대상이 된다 |
| `cancelled` | 배송 전에 취소됐다 |
| `return_requested` | 배송 후에 반품이 접수됐다 |
| `returned` | 반품이 끝났다 |

취소와 반품을 가르는 것은 **배송완료 시각**이다. 용어 정의는 `glossary.md` 에 있다.

`delivered` 시점에 두 값을 박제한다(`D10`).

| 값 | 계산 |
|---|---|
| 청약철회 만료일 | 배송완료 다음날부터 7일, 말일이 쉬는 날이면 다음 영업일 |
| 자동 구매확정 예정일 | 배송완료 다음날부터 8일, 같은 규칙 |

## 누가 옮기나

| 전이 | 주체 |
|---|---|
| `payment_pending` → `paid` | 결제 모듈. 사람이 직접 못 옮긴다 |
| `payment_pending` → `payment_expired` | 배치 |
| `preparing` → `shipping` → `delivered` | 셀러 |
| `preparing` → `cancelled` | 고객 또는 셀러 |
| `delivered` → `return_requested` | 고객 |
| `return_requested` → `returned` | 셀러 |
| `delivered` → `confirmed` | 고객 또는 배치 |
| 그 밖의 모든 전이 | 관리자만. 감사 로그를 남긴다 |

### 셀러는 자기 것만 옮긴다

`scope=seller` 가 판정한다. 판정 엔진은 이미 있고(청크 4), 상태 조건이 청크 11a 에서 붙는다.

**배송 후에는 셀러도 못 고친다.** `delivered` 를 지나면 셀러의 전이 권한이 닫힌다.
셀러가 배송완료를 되돌릴 수 있으면 청약철회 기산점을 조작할 수 있다.

### 관리자 강제 전이

정상 전이표를 벗어나는 이동은 관리자만 한다. CS 처리에 필요하다.

**감사 로그가 필수다**(청크 4b). 강제 전이는 정상 경로가 아니라서
왜 그랬는지가 남지 않으면 나중에 데이터가 왜 이 모양인지 아무도 모른다.

### 상태 이력을 남긴다

ADR 0007 이 정한 이력 테이블에 전이가 쌓인다.
현재 상태만 들고 있으면 "언제 배송됐나" 를 답할 수 없고, 청약철회 기간 분쟁에 근거가 없다.

## 자동 전이 둘

| 전이 | 언제 | 도는 주기 |
|---|---|---|
| `payment_pending` → `payment_expired` | 생성 후 30분 | **5분마다** |
| `delivered` → `confirmed` | 자동확정 예정일 경과 | 매일 04:00 |

### 결제 만료는 `D10` 의 예외다

`D10` 은 배치를 04:00 에 돌린다. 결제 만료는 그 규칙에서 빠진다.

하루에 한 번 돌면 재고가 하루 종일 잡혀 있다. 만료 판정은 **경과 시간**이라
「전날 24시 기준」 같은 고정 기준이 필요 없고, 여러 번 돌아도 결과가 같다.

### 자동확정 8일

청약철회 7일 바로 다음날이다. 반품할 수 있는 주문이 확정되는 일이 없다.

**틈이 좁아서 경계를 정확히 해야 한다.** 청약철회 마감일에 접수된 반품과
다음날 새벽 확정 배치가 붙어 있다.

```
배송완료 8/6
  청약철회 만료   8/13 23:59:59
  자동확정 배치   8/14 04:00
```

배치는 `return_requested` 상태를 건드리지 않는다. 반품이 접수돼 있으면 확정 대상에서 빠진다.

## 상품 상태

| 상태 | 뜻 |
|---|---|
| `draft` | 셀러가 작성 중이다. 노출되지 않는다 |
| `pending_review` | 검수를 기다린다 |
| `on_sale` | 판매 중이다 |
| `sold_out` | 재고가 없다 |
| `suspended` | 판매가 중지됐다 |

검수는 청크 7c 다. 관리자가 승인해야 `on_sale` 이 된다.

`sold_out` 은 재고에서 파생되지만 상태로 둔다. 목록 조회에서 매번 재고를 세면 쿼리가 무거워진다.

**삭제는 여기 없다.** `deleted_at` 이 따로 있다(`domain-model.md`).

## 안 다루는 것

| 항목 | 왜 |
|---|---|
| 항목 단위 부분 취소 | 최소 단위를 `seller_order` 로 정했다 |
| 교환 | 반품 후 재주문으로 대신한다. 전이가 두 배로 는다 |
| 배송 추적 연동 | 택배사 API 가 없다. 셀러가 직접 `delivered` 로 옮긴다 |
| 정산·문의 상태머신 | 청크 17·54 에서 그때 정한다 |

## 이 문서를 고칠 때

새 상태를 넣기 전에 **그게 업무 상태인지 수명인지** 먼저 가른다(`domain-model.md`).
전이를 추가하면 주체를 위 표에 같이 적는다. 주체가 안 정해진 전이는 결국 관리자만 하게 된다.
