# 식별자 규약

내부에서 쓰는 ID 와 바깥에 내보내는 번호를 어떻게 가르는지 정한다.

## 두 가지를 가른다

| | 내부 ID | 노출 번호 |
|---|---|---|
| 예 | `orders.id = 4837` | `20260805-4F2K91` |
| 타입 | `bigint generated always as identity` | `text` |
| 쓰는 곳 | 외래키, 조인, 인덱스 | URL, 화면, CS, 이메일 |
| 성질 | 순번 | 순번 정보가 없다 |

내부 ID 를 그대로 노출하지 않는 자원이 있다. 아래 표에 적는다.

## 순번을 노출하면 새는 것

순번은 **총량과 증가 속도**를 알려준다.

```
1월 1일에 주문 → 번호 10000
1월 31일에 주문 → 번호 13500

한 달 주문 3500건. 객단가를 곱하면 거래액이 추정된다
```

계정 하나로 두 번 주문하면 경쟁사의 매출 규모를 알아낼 수 있다.
2차대전 때 노획한 전차의 일련번호로 독일의 생산량을 추정한 데서 **독일 전차 문제**라고 부른다.

상용 쇼핑몰 솔루션이 주문번호 뒷부분을 난수로 만드는 이유가 이것이다.

## 주문번호

```
20260805-4F2K91
└──날짜──┘ └난수┘
```

| 부분 | 내용 | 왜 |
|---|---|---|
| 날짜 8자리 | 주문 생성일 (KST 기준) | CS 용. 고객이 번호를 부르면 언제 주문인지 바로 보인다. 고객도 아는 정보라 노출돼도 무해하다 |
| 구분자 | 하이픈 | 눈으로 읽기 쉽다 |
| 난수 6자리 | 대문자 + 숫자 | 순번을 가린다 |

### 난수의 조건

**`SecureRandom` 을 쓴다.** `Random` 은 앞의 출력 몇 개로 다음 값이 계산된다.
예측 가능한 주문번호는 순번만큼은 아니어도 정보가 샌다. 비용 차이가 없으므로 안전한 쪽을 쓴다.

**혼동되는 문자를 뺀다.** `0`·`O`, `1`·`I` 를 빼면 32자가 남는다.
전화로 번호를 불러주는 상황에서 잘못 듣는 것을 줄인다.

`32^6 = 약 10억` 조합이다. 하루 1만 건 주문에서 충돌이 날 확률이 수 퍼센트고,
유니크 인덱스가 막으면 다시 뽑는다. 재시도는 3회까지 하고 그래도 실패하면 오류를 낸다.

### 주문번호로 조회하지 않는다

주문번호를 알면 주문이 보이는 경로를 만들지 않는다. 번호가 곧 인증이 되면 안 된다.
조회는 로그인한 사용자의 권한 판정을 거친다.

비회원 주문 조회가 필요해지면 번호 + 다른 정보(연락처 뒷자리 등)를 같이 요구한다.

## 자원별 노출 방식

| 자원 | 노출 | 왜 |
|---|---|---|
| 주문 | **`order_number`** | 총량이 새면 안 된다 |
| 결제 | **`payment_number`** | 주문과 같다. 형식도 같다 |
| 정산 | **`settlement_number`** | 셀러별 정산 건수가 새면 매출 추정에 쓰인다 |
| 상품 | 내부 ID | 총 상품 수는 목록에서 세면 나온다. 숨길 이유가 없다 |
| 셀러 | `code` (기존) | 이미 사람이 정하는 값이 있다 |
| 사용자 | 내부 ID | 가입자 수는 숨기고 싶지만, 계정 조회는 권한이 막는다. 필요해지면 그때 바꾼다 |
| 역할·권한 | `code` | 관리용이고 사람이 읽는 값이다 |

**노출 번호가 있는 자원은 URL 에도 그것을 쓴다.**

```
GET /api/orders/20260805-4F2K91      맞다
GET /api/orders/4837                 안 쓴다
```

내부 ID 를 URL 에 쓰면 노출 번호를 둔 의미가 없다.

## 내부 ID

`bigint generated always as identity` 를 쓴다. 지금 모든 테이블이 그렇다.

UUID 를 기본키로 쓰지 않는다. 이유가 둘이다.

- `bigint` 는 8바이트, UUID 는 16바이트다. 외래키가 많은 스키마에서 인덱스 크기가 두 배가 된다
- 조인과 정렬이 정수 비교라 빠르다

UUIDv7(RFC 9562)이 시간순 정렬을 지원해서 UUID 의 인덱스 지역성 문제를 풀지만,
**우리는 분산 시스템이 아니라서 ID 를 여러 곳에서 만들 일이 없다.** DB 가 순번을 주면 된다.

## 멱등키

청크 12(모의 결제)가 쓴다. 형식은 D11 에서 정하지만 여기 적어 둔다.

- **클라이언트가 만든다.** 서버가 주면 멱등이 성립하지 않는다
- UUIDv4 를 권장한다. Stripe 도 그렇게 한다
- 최대 255자
- **개인정보를 넣지 않는다.** 이메일이나 전화번호를 키로 쓰면 로그에 남는다

## 이 문서를 고칠 때

노출 번호 형식은 **한 번 내보내면 못 바꾼다.** 고객이 저장하고 CS 가 검색하고 이메일에 남는다.
바꿔야 하면 새 형식을 추가하고 옛 번호를 계속 조회 가능하게 둔다.

새 자원이 생길 때 노출 방식을 이 표에 추가한다. 안 적으면 내부 ID 가 그냥 나간다.
