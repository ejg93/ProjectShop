# 성능 목표

목록 입구의 쿼리 수·실행 계획·응답 p95 를 로컬 10만 건에서 재어 기준선으로 두고, 같은 기계의 다음 측정이
기준선 +50% 를 넘으면 회귀로 본다(`D21`).

## 왜 절대 수치가 아닌가

데모 트래픽이라 운영에서 읽을 값이 없고, 로컬 수치는 기계마다 다르다. 그래서 **같은 기계에서 잰 앞 값과 견준다**
(2026-09-23 사용자 결정). 「200ms 안」 같은 절대 목표를 적으면 기계가 바뀌는 날 근거 없이 빨갛거나 초록이 된다.

**재는 것은 셋이고 성격이 다르다.**

| 무엇 | 무엇을 막나 | 어디서 잰다 |
|---|---|---|
| 쿼리 수 | N+1 — 쪽 크기를 늘리면 문장이 느는 것 | `QueryBudgetTest`(느린 레인, 늘 돈다) |
| 실행 계획 | 순차 스캔·인덱스 누락 — 데이터가 늘면 느려지는 모양 | `42` 의 측정(손으로, `doc/notes/perf-local-100k.md`) |
| 응답 p95 | 위 둘이 못 보는 회귀 — 질의 모양이 바뀌어 같은 수의 문장이 느려지는 것 | `70` 의 부하(손으로, `bash scripts/load-test.sh`) |

## 쿼리 수 예산

**`QueryBudgetTest` 가 든다**(`Q204`·`Q204b`). 목록은 쪽 크기 1 과 50 에서 문장 수가 같고 `BUDGET` 이하다.
상세는 묶음·품목이 1 일 때와 3 일 때 문장 수가 같다. 넘는 입구는 `OVER_BUDGET` 에 근거와 함께 적는다.
수는 그 시험의 `LISTS` 가 원본이고 여기 옮기지 않는다 — 두 곳에 두면 한쪽이 낡는다.

## 데이터 규모 가정

`bash scripts/load-data.sh` 가 만드는 `shop_load`(`70-0`)다. 건수는 재현된다 — `random()` 을 안 쓴다.

| 표 | 수 | 분포 |
|---|---|---|
| 주문 | 10만 | 최근 90일에 고르게, 90% 결제·4% 대기·3% 만료·3% 실패 |
| 묶음 | 12만 | 주문마다 셀러 하나, 다섯 중 하나는 둘 |
| 항목 | 20만 | 묶음마다 하나 또는 둘 |
| 상품·SKU | 1만·3만 | 데모 셀러 둘에 반씩, 90% `on_sale` |
| 구매자 | 1,000(합성) + 데모 고객 | 데모 고객이 주문의 1%(1,000 건)를 가진다 — 한 사람에게 몰면 내 주문 계획이 왜곡된다 |
| 환불 | 8,000 | 결제된 주문의 취소·반품 묶음마다 하나, 요청 상태 |

**앱이 고쳐 쓸 행을 안 둔다.** 30분 넘은 결제 대기나 환불 없는 닫힌 취소 묶음을 넣으면 앱의 주기 작업이 재는 도중에 메워서
회차마다 데이터가 갈린다(`stack.md` 「부하 데이터는 `shop_load` 에 붓는다」). 그래서 `load-test.sh` 는 **매번 새로 붓는다.**

**규모를 바꾸면 기준선을 다시 잰다.** 같은 질의도 행 수가 바뀌면 계획이 바뀐다.

## 재는 방법

| 무엇 | 어떻게 |
|---|---|
| 실행 계획 | `POSTGRES_DB=shop_load` 로 `bootRun`, 흐름을 지나 `pg_stat_statements` 상위 20 과 `auto_explain` 을 본다. 절차와 결과는 `doc/notes/perf-local-100k.md` |
| 응답 p95 | `bash scripts/load-test.sh` — 컴포즈의 backend 이미지(`load` 프로필)에 k6 를 세 번 걸고 입구별 p95 의 중앙값을 기준선과 견준다(`70`). `bootRun` 에 안 거는 이유는 IDE·JIT 워밍이 수치를 흔들어서다 |

**요청 제한을 끄고 잰다**(`RATE_LIMIT_ENABLED=false`). 제한이 주소당 1분 120 이라 켜 두면 부하가 429 를 잰다.

## 기준선

입구마다 `42` 의 주 질의 평균(`V120` 뒤)과 `70` 의 p95 다. **p95 칸의 원본은 `load/baseline.json` 이고 이 표는 사본이다** —
`70` 의 대조 시험이 둘을 견준다. 키는 그 JSON 의 이름이다.

| 입구 | 키 | 경로 | 주 질의 평균(ms) | p95(ms) |
|---|---|---|---|---|
| 상품 공개 목록 | `products` | `GET /api/products` | 34.4 | 77.2 |
| 상품 검색 | `search` | `GET /api/products?q=` | 미측정 — `42` 뒤에 섰다 | 26.3 |
| 내 주문 목록 | `my_orders` | `GET /api/orders` | 0.3 | 16.4 |
| 셀러 주문 목록 | `seller_orders` | `GET /api/seller/orders` | 34.7 | 169 |
| 관리자 주문 목록 | `admin_orders` | `GET /api/admin/orders` | 0.4 | 25.1 |
| 정산서 목록 | `settlements` | `GET /api/settlements` | 0.1 | 14.2 |

p95 는 2026-10-02 에 VU 10·1분·세 회차 중앙값으로 쟀다(`load/README.md` 의 기계). 검색어는 「운동화」(상품 1만 중 1,250 건이 맞는다).

상품 공개 목록과 셀러 주문 목록이 무거운 이유는 질의 모양이다(`Q243`). 고치면 이 표와 기준선을 같이 옮긴다.

## 회귀 문턱

**p95 가 기준선의 1.5배를 넘으면 빨강이다**(2026-09-23 사용자 결정). 한 번이 아니라 세 번 돌린 중앙값으로 견준다 —
로컬 Docker 는 회차마다 흔들려서 한 번으로 재면 잡음이 회귀로 읽힌다.

**VU 는 10 이다.** 처음 20 으로 쟀더니 0.3ms 질의의 p95 가 100ms 를 넘었고(질의가 아니라 컨테이너의 줄 서기를 잰다)
세 회차 중 하나가 모든 입구에서 30% 넘게 느렸다(2026-10-02). 그 회차에 앱의 쓰기는 없었다 — 기계의 흔들림이다.

**문턱을 숨겨 올리지 않는다.** 흔들림이 문턱을 자주 넘으면 VU 를 줄이거나 문턱을 이 절에서 고치고 이유를 적는다.

## 기준선을 옮길 때

질의를 일부러 고쳐 빨라졌거나 규모를 바꿨을 때다. `bash scripts/load-test.sh --update-baseline` 으로 JSON 을 다시 쓰고
**같은 커밋에서 위 표를 고친다.** 느려진 것을 기준선으로 덮지 않는다 — 그것이 이 문서가 막는 일이다.
