# API 설계 규약

우리가 정한 것만 적는다. **여기 없는 것은 Zalando RESTful API Guidelines 를 따른다.**
링크는 `external-references.md` 에 있다.

통째로 베끼지 않는 이유는 유지 때문이다. 수백 개를 옮겨 적으면 원본이 바뀌었을 때 어긋난 채로 남는다.

## 기준에서 벗어난 것

먼저 적는다. 벗어난 것을 뒤에 묻어 두면 못 찾는다.

| 항목 | Zalando | 우리 | 왜 |
|---|---|---|---|
| 페이징 | 커서 기반 권장 (SHOULD) | **오프셋 기반** | 커서는 정렬 키가 고정돼야 하고 임의 페이지 이동이 안 된다. 관리자 화면(청크 16)이 페이지 번호를 쓴다. 데이터 규모가 작아 오프셋의 성능 문제가 안 온다 |
| 전체 개수 | 안 주는 것을 권장 (SHOULD) | **준다** | 위와 같은 이유. 관리자 화면에 총 건수가 필요하다 |

둘 다 `SHOULD` 라 벗어날 수 있다. 청크 42(성능 튜닝)나 70(부하 테스트)에서 오프셋이 실제로 문제가 되면 그때 커서로 바꾼다.

`MUST` 는 벗어나지 않는다. 벗어날 거면 기준으로 삼은 의미가 없어진다.

## 이름

### JSON 속성은 snake_case

Zalando 의 `MUST` 다. Java 필드는 camelCase 로 두고 **직렬화할 때만** 바꾼다.

```yaml
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

설정 한 줄이라 비용이 없고, 얻는 것이 있다. **DB 컬럼 이름과 JSON 필드 이름이 같아진다.**

```
DB          created_at, password_hash, is_org_role
JSON        created_at, password_hash, is_org_role
Java 필드    createdAt, passwordHash, isOrgRole
```

이름이 바뀌는 자리가 Java 안쪽 하나뿐이라, 로그와 쿼리와 응답을 같은 말로 읽을 수 있다.

### URL

- 자원은 **복수형 명사**. `/api/products`, `/api/orders`
- 동사를 쓰지 않는다. `/api/getProduct` 안 됨
- 여러 단어는 하이픈. `/api/order-items`
- 소문자만 쓴다

## 메서드

| 메서드 | 쓰는 곳 |
|---|---|
| GET | 조회. 부수 효과 없음 |
| POST | 생성. 그리고 아래 「동작」 |
| PUT | 전체 교체. 잘 안 쓴다 |
| PATCH | 부분 수정. 수정은 기본적으로 이쪽 |
| DELETE | 삭제 |

## 상태 코드

| 코드 | 언제 |
|---|---|
| 200 | 조회·수정 성공 |
| 201 | 생성 성공. `Location` 헤더에 새 자원 경로 |
| 204 | 성공했고 돌려줄 본문이 없음 |
| 400 | 요청 형식이 틀림 |
| 401 | 로그인 안 됨 |
| 403 / 404 | 권한 없음. **어느 쪽을 줄지는 자원마다 다르다.** 아래 「권한 실패」 |
| 409 | 상태가 안 맞음. 허용되지 않은 상태 전이, 재고 부족 |
| 422 | 형식은 맞는데 값이 규칙에 안 맞음 |

## 오류 본문

**RFC 9457 Problem Details.** `application/problem+json` 으로 내보낸다.

```json
{
  "type": "https://example.com/probs/insufficient-scope",
  "title": "권한이 부족하다",
  "status": 403,
  "detail": "이 주문은 다른 셀러의 것이다",
  "instance": "/api/orders/4837"
}
```

Spring Framework 6 부터 `ProblemDetail` 이 있으므로 직접 만들지 않는다.

```yaml
spring:
  mvc:
    problemdetails:
      enabled: true
```

`type` 이 URI 라서 오류 종류마다 설명 문서를 가리킬 수 있다. **프론트는 상태 코드가 아니라 `type` 으로 분기한다.**
상태 코드는 종류가 적어서 서로 다른 오류가 같은 코드로 뭉친다.

## 목록 조회

### 요청

| 파라미터 | 뜻 | 기본값 |
|---|---|---|
| `page` | 0 부터 시작하는 페이지 번호 | 0 |
| `size` | 한 페이지 크기 | 20 |
| `sort` | `필드,방향`. 예: `created_at,desc` | 자원마다 정함 |

`size` 의 최대값을 100 으로 막는다. 안 막으면 목록 하나로 전체를 긁어 갈 수 있다.

### 응답

```json
{
  "items": [ ... ],
  "page": 0,
  "size": 20,
  "total": 137
}
```

껍데기 이름을 하나로 고정한다. `data`·`list`·`content` 를 섞어 쓰면 프론트가 엔드포인트마다 다른 코드를 쓴다.

**빈 목록은 `[]` 다.** `null` 을 주지 않는다.

## 값의 형식

| 종류 | 형식 | 예 |
|---|---|---|
| 시각 | RFC 3339 (ISO 8601). 오프셋 포함 | `2026-08-05T14:30:00+09:00` |
| 날짜 | `YYYY-MM-DD` | `2026-08-05` |
| 금액 | 정수. 원 단위 | `15000` |
| 열거값 | 대문자 스네이크 | `PAID`, `SHIPPING_READY` |

금액을 문자열로 주는 방식도 있지만(정밀도 손실 방지) 원화는 정수라 해당이 없다.
자세한 것은 D8 금액 규약에서 정한다.

## null 과 생략

Zalando 의 `MUST` — **없는 것과 `null` 에 다른 뜻을 주지 않는다.**

이 규칙이 우리 필드 마스킹(청크 4d)과 정면으로 만난다.

셀러가 주문을 볼 때 결제 수단이 안 보인다. 응답에 어떻게 나가야 하나.

| 방법 | 문제 |
|---|---|
| `"payment_method": null` | "권한이 없어서 안 보임" 과 "결제 수단이 아직 없음" 이 구분 안 된다 |
| 필드를 아예 생략 | 클라이언트가 필드 없음을 권한 문제인지 값 없음인지 모른다 |

**생략하되, 무엇이 보이는지를 같이 알려준다.**

```json
{
  "id": 4837,
  "total_amount": 15000,
  "recipient_name": "홍길동",
  "_visible_field_groups": ["basic", "shipping"]
}
```

`payment` 그룹이 목록에 없으므로 결제 관련 필드가 빠진 것이 **권한 때문**임이 드러난다.
필드가 있는데 값이 없으면 그건 진짜로 값이 없는 것이다.

밑줄로 시작하는 이름은 메타 필드라는 표시다. 자원의 속성이 아니다.

## 권한 실패 — 403 이냐 404 냐

403 을 주면 **그 자원이 존재한다는 사실이 샌다.** 번호를 훑으면 실재하는 번호의 지도가 그려진다.
404 를 주면 정보는 안 새지만 클라이언트가 권한 문제인지 오탈자인지 모른다.

자원의 민감도로 가른다.

| 자원 | 권한 없을 때 | 왜 |
|---|---|---|
| 상품 | **403** | 어차피 공개 목록에 있다. 존재를 숨길 이유가 없다 |
| 주문 | **404** | 주문 수와 증가 속도가 새면 안 된다 |
| 결제 | **404** | 주문과 같다 |
| 사용자 | **404** | 계정 존재 여부는 가입 시도로 알 수 있지만 굳이 알려주지 않는다 |
| 셀러 | **403** | 공개 정보다 |
| 역할·권한 | **403** | 관리 기능이라 접근한 사람이 이미 로그인 상태다 |

로그인 자체가 안 됐으면 **401** 이다. 이건 자원과 무관하다.

### 판정 결과와의 대응

`permission-rules.md` 가 적어 둔 문제 — 우리 `Decision` 은 "거부 규칙이 있어서 거부" 와
"규칙이 없어서 거부" 를 같은 값으로 뭉치고 있다.

**응답은 둘을 구분하지 않는다.** 위 표대로 자원별로만 가른다.
구분해서 내보내면 "당신에게는 명시적 거부가 걸려 있다" 는 정보가 새고, 그것도 권한 구조의 노출이다.

내부적으로 구분하는 것은 필요하다. 감사 로그(청크 4b)에는 어느 규칙이 이겼는지가 남아야 한다.

### 판정 자체가 실패하면

DB 조회가 실패하는 등 판정을 못 한 경우다. XACML 의 `Indeterminate` 에 해당한다.

**거부로 떨어뜨리고 500 을 준다.** 허용으로 떨어지면 안 된다.
권한 판정이 고장 났을 때 열리는 시스템은 고장 자체가 공격 수단이 된다.

## 동작 — CRUD 가 아닌 것

주문 취소, 배송 시작, 정산 확정 같은 것이다. 자원의 생성·수정으로 표현이 안 된다.

**하위 경로에 POST 한다.**

```
POST /api/orders/{id}/cancel
POST /api/orders/{id}/ship
POST /api/settlements/{id}/confirm
```

`PATCH /api/orders/{id}` 로 `status` 를 바꾸는 방식은 쓰지 않는다.
전이표를 거치지 않는 상태 변경 경로가 생기기 때문이다(ADR 0009).
상태는 **동작의 결과**지 클라이언트가 정하는 값이 아니다.

허용되지 않은 전이는 **409** 다.

## 버전

**지금은 버전을 안 붙인다.** `/api/orders` 로 간다.

붙일 시점이 오면(청크 72) 그때 `/api/v2/...` 를 추가하고 기존 경로를 v1 으로 남긴다.
지금 `/api/v1/` 을 붙이면 쓰지도 않을 버전 체계를 이고 간다.

호환을 깨는 변경의 기준은 Zalando 의 호환성 장을 따른다.

## 헤더

| 헤더 | 용도 |
|---|---|
| `traceparent` | 요청 추적. W3C Trace Context 형식 (D16) |
| `Idempotency-Key` | 멱등 요청. POST 에만 (D11, 청크 12) |
| `Location` | 201 응답에서 새 자원 경로 |

자체 헤더를 만들 때는 `X-` 를 붙이지 않는다. RFC 6648 이 그 관행을 폐기했다.

## 인증

세션 쿠키다. `HttpOnly` + `SameSite`. 토큰을 헤더로 받지 않는다.
근거는 `PLAN.md` 의 「인증은 세션 쿠키, JWT 아님」에 있다.

쿠키를 골랐으므로 CSRF 토큰이 필요하다(청크 5b). 쓰기 요청은 토큰을 같이 보낸다.

## 이 문서를 고칠 때

새 규칙이 필요해지면 여기 추가하고, Zalando 에 이미 있는 규칙이면 **적지 말고 따른다.**
중복해서 적으면 원본이 바뀌었을 때 어느 쪽이 맞는지 모르게 된다.

기준을 벗어날 때는 맨 위 표에 추가한다. 벗어난 사실이 한 군데 모여 있어야 나중에 되돌릴 수 있다.
