# 0004. 권한 축을 넷으로 늘린다

- 날짜: 2026-08-03
- 상태: 채택

## 결정

역할 3개 × 스코프 한 겹이던 모델에 축 네 개를 더한다. 청크 9개가 계획에 추가됐다.

| 축 | 무엇이 바뀌나 | 청크 |
|---|---|---|
| 셀러 조직 | 역할 부여에 대상이 붙는다. "A셀러의 CS 담당" | 3a, 5a, 16a |
| 거부 규칙 | 같은 권한이 allow와 deny로 잡히면 deny가 이긴다 | 3b |
| 상태 조건 | 자원의 상태가 역할과 무관하게 권한을 깎는다 | 11a |
| 캐시 무효화 | 역할 회수가 즉시 먹는지 검증한다 | 4a |

여기에 감사 로그(4b), 환불 승인 분리(12a), 임퍼소네이션(16b)이 붙는다.

## 왜 늘렸나

청크 3까지 만들고 보니 판정할 것이 없었다. `scope=seller` 는 셀러가 실체로 없어서 `own` 과 구분되지 않고,
허용만 쌓이는 구조라 우선순위 문제가 안 생긴다. 이대로 청크 4를 하면 판정 엔진이 조인 한 번으로 끝난다.

권한 체계를 익히려고 만든 프로젝트인데 정작 어려운 부분이 빠져 있었다.
실무에서 권한이 지저분해지는 원인은 역할이 많아서가 아니라 축이 겹쳐서다.

## 저울질한 것

역할을 늘리는 방법도 있었다. CS 담당, 정산 담당, 감사자를 추가하면 역할이 6개가 된다.
그런데 그건 `role` 테이블에 행을 넣는 일이라 이미 지금 스키마로 되고, 판정 코드는 한 줄도 안 바뀐다.
데이터로 되는 것을 계획에 적을 이유가 없다.

축을 늘리면 판정 코드가 바뀐다. 조직 컨텍스트가 없으면 판정 함수의 입력 자체가 달라지고,
deny가 들어오면 결과를 모아서 우선순위를 매기는 단계가 생긴다.

## 따라오는 제약

- 청크 4는 3a·3b를 선행으로 갖는다. 조직과 거부를 나중에 끼우면 판정 함수를 다시 짜야 한다
- 청크 6의 상품 주인이 사람이 아니라 셀러가 된다. `product.seller_id` 는 `app_user` 가 아니라 `seller` 를 가리킨다
- 캐시(4a)를 넣은 뒤로는 권한을 바꾸는 모든 경로가 무효화를 호출해야 한다. 빠뜨리면 회수가 안 먹는다
- 번호에 글자를 붙여 끼웠다. 앞 번호를 밀면 `PROGRESS.md` 의 완료 기록과 어긋난다
