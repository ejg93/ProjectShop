# 0006. 인증 방어와 권한 검증을 청크로 세운다

- 날짜: 2026-08-04
- 상태: 채택

## 결정

계획에 청크 9개를 더한다. 앞의 다섯은 판정을 지키는 장치이고, 뒤의 넷은 그 주변을 메운다.

| 청크 | 무엇 | 선행 |
|---|---|---|
| 4c | 권한 매트릭스 회귀 테스트 | 4 |
| 5b | CSRF 방어 | 5 |
| 7b | 권한 실패 응답 규약 | 4, 7, 2a |
| 8a | 내 권한 목록 API | 4, 5 |
| 13b | 화면 권한 반영 | 8a, 13 |
| 5c | 인증 실패 경로 | 5 |
| 6b | 데모 시드 데이터 | 3a, 3c, 6 |
| 10b | 재고 경쟁 테스트 | 10 |
| 2b | 로그·요청 추적 규약 | 2 |

4c는 4a보다 먼저 한다. 캐시를 넣기 전에 판정 결과가 고정돼 있어야 캐시가 판정을 바꿨는지 알 수 있다.

## 왜 넣었나

### 판정을 만드는 것과 지키는 것은 다르다

청크 4가 판정 엔진을 만들지만, 그게 계속 맞는지 확인하는 장치가 없었다.
축이 다섯이다. 역할 × 스코프 × allow/deny × 자원 상태 × 조직 소속. 조합이 수백 개고 손으로 다 못 쓴다.

실무에서 권한이 무너지는 원인은 판정 로직이 틀려서가 아니라 바뀐 걸 아무도 모르기 때문이다.
매트릭스를 파일로 떠서 고정하면 판정이 바뀔 때 diff 가 뜬다.
"정산 담당 권한을 손봤더니 CS 담당이 남의 주문을 보게 됐다" 가 리뷰에서 잡히는 자리다.

### 세션 쿠키를 고른 대가를 안 갚았다

쿠키를 고른 근거는 즉시 회수였다. 그 선택이 CSRF 를 데려온다.
브라우저가 쿠키를 자동으로 붙여 보내니 남의 사이트에서 쏜 요청도 인증을 통과한다.
토큰을 헤더에 넣는 방식에서는 안 생기고, 쿠키를 고르면 반드시 따라온다.

계획에 `SameSite` 언급은 있었지만 그것만으로 안 끝난다.
`Lax` 는 최상위 GET 을 통과시키고, 서브도메인과 구형 브라우저에 예외가 있다.

회수를 즉시 먹게 만드는 데 청크를 쓰면서(4a) 그 선택이 연 구멍을 안 막으면 앞뒤가 안 맞는다.

### 판정을 두 벌 만들지 않으려면 서버가 내려줘야 한다

화면은 버튼을 보여줄지 말지를 알아야 한다. 그런데 프론트에서 `role === 'seller'` 로 판단하기 시작하면
서버 규칙과 화면 규칙이 갈라진다. 서버 쪽을 고쳐도 화면이 안 따라오고,
그게 이 프로젝트가 피하려는 실패 방식 그대로다.

서버가 권한 목록을 계산해 내려주고(8a) 화면은 그것만 본다(13b).

### 403 은 정보를 흘린다

남의 주문에 403 을 주면 그 주문이 존재한다는 사실이 샌다. 번호를 1부터 찍으면 실재하는 번호를 알아낼 수 있다.
404 를 주면 정보는 안 새지만 클라이언트가 권한 문제인지 오탈자인지 구분을 못 한다.

정답이 하나가 아니라 자원마다 다르게 간다. 안 정해 두면 컨트롤러마다 개발자 취향으로 갈리고,
그건 권한이 코드에 흩어지는 것과 같은 실패다.

응답 본문의 형식은 RFC 9457(Problem Details for HTTP APIs)을 쓴다. 2023년에 RFC 7807 을 대체한 표준이다.
`type`·`title`·`status`·`detail`·`instance` 를 `application/problem+json` 으로 내보낸다.
`type` 이 URI 라서 오류 종류마다 설명 문서를 가리킬 수 있고, 프론트는 상태 코드 대신 이 값으로 분기한다.

Spring Framework 6 부터 `ProblemDetail` 이 들어와서 이 프로젝트의 Boot 4.1 에서는 그대로 쓴다.
직접 만든 `{"error": "..."}` 형식을 쓰면 프론트가 서비스마다 다른 껍데기를 벗겨야 하고, 표준 도구가 못 읽는다.

## 판단해서 더 넣은 것

5c·6b·10b·2b 는 위 다섯만큼 급하지 않지만 나중에 끼우면 이미 짠 것을 다시 쓰게 된다.

- **5c** — 로그인 실패 제한과 세션 ID 재발급은 인증을 다 만든 뒤에 넣으면 로그인 경로를 다시 뜯는다
- **6b** — 셀러 2곳에 역할이 겹친 데이터가 없으면 관리자 화면을 만들어도 눈으로 볼 판정이 없다
- **10b** — 청크 10에 "동시성 처리" 한 줄이 있었는데, 락을 골랐다는 것과 경쟁에서 안 깨진다는 것은 다른 얘기다
- **2b** — 감사 로그(4b)는 권한 변경을 남기고, 이건 요청 하나를 끝까지 따라가는 용도다

## 저울질한 것

권한 테스트를 케이스마다 손으로 쓰는 방법이 있었다. 읽기 쉽고 실패 메시지가 친절하다.
그런데 조합이 수백 개라 다 못 쓰고, 안 쓴 조합이 정확히 구멍이 된다.
매트릭스를 뜨면 읽기는 덜 친절해도 빠진 조합이 없다.

8a 를 화면 청크(13)에 붙이는 방법도 있었다. 그런데 이건 판정 엔진의 출력을 밖으로 내보내는 API 라
프론트보다 백엔드 쪽 결정이고, 화면 없이 테스트로 검증할 수 있다.

## 따라오는 제약

- 4c 를 만든 뒤로는 판정을 바꿀 때마다 매트릭스 파일이 같이 바뀐다. diff 를 안 보고 갱신하면 장치가 무의미해진다
- 5b 를 켜면 프론트의 모든 쓰기 요청이 토큰을 실어야 한다. 청크 13 프록시 설정과 묶인다
- 7b 의 규약은 `2a` 문서에 실려야 한다. 문서에 없으면 다음 API 를 짜는 사람이 또 취향대로 고른다
- 13b 이후 화면에서 역할 이름을 직접 쓰는 코드는 금지다. 한 군데라도 새면 판정이 두 벌이 된다
