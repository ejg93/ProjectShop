# 0009. 공휴일은 데이터로, 전이표는 코드로 둔다

- 날짜: 2026-08-05
- 상태: 채택

## 결정

기준 자료가 없는 문서 둘에서 지금 정할 수 있는 것을 정한다.

| 문서 | 결정 |
|---|---|
| D10 시각·영업일 | 공휴일을 테이블에 두고 운영 중에 추가할 수 있게 한다 |
| D7 상태머신 | 주문 전이표를 코드에 선언한다 |

둘 다 "바뀌는 것이냐" 를 기준으로 갈랐다. 방향이 반대로 나왔다.

## 공휴일 — 바뀐다

`commerce-compliance.md` 의 R5 는 청약철회 환급을 **3영업일** 안에 하라고 한다.
영업일을 세려면 공휴일을 알아야 하는데, 한국 공휴일은 종류마다 성격이 다르다.

| 종류 | 성격 |
|---|---|
| 고정 공휴일 | 신정·삼일절·광복절 등. 날짜가 정해져 있다 |
| 음력 공휴일 | 설·추석. 매년 양력 날짜가 다르다 |
| 대체공휴일 | 규칙이 있고, 그 규칙이 개정된다 |
| **임시공휴일** | **정부가 그해에 정한다. 한두 달 전에 결정되는 경우가 있다** |

임시공휴일이 결정을 갈랐다. 코드나 마이그레이션에 박아 두면 지정될 때마다 배포해야 한다.
공휴일 하나 때문에 배포하는 건 위험 대비 이득이 없다.

`holiday` 테이블을 두고 행을 추가한다. 고정·음력 공휴일은 마이그레이션으로 몇 년치를 넣고,
임시공휴일은 지정될 때 행만 넣는다.

권한을 데이터로 둔 것과 같은 논리다. **바뀌는 것을 코드에 박지 않는다.**

### 따라오는 것

- 공휴일을 추가하는 권한이 생긴다. `holiday:manage` 같은 것
- 관리자 화면에 공휴일 편집이 붙는다. 청크 16 이후
- **이미 계산된 기한이 소급되는지**는 D10 에서 정한다.
  임시공휴일이 지정됐을 때 진행 중인 환불의 기한이 밀리나, 아니면 계산 시점의 달력을 따르나.
  기한을 저장해 두면 안 밀리고, 매번 계산하면 밀린다

### 날짜 세는 방식이 두 가지라는 것

같은 도메인에 달력일과 영업일이 같이 있다. 이걸 흐리면 개발자마다 다르게 계산한다.

| 기한 | 방식 | 근거 |
|---|---|---|
| 청약철회 7일 | 달력일 | 법이 "7일" 이라고 쓴다. 주말·공휴일을 센다 |
| 환급 3영업일 | 영업일 | 주말과 공휴일을 뺀다 |

## 전이표 — 안 바뀐다

주문 상태 전이는 도메인 규칙이다. "배송완료에서 결제대기로 갈 수 있나" 의 답은 사업이 바뀌어야 바뀐다.
운영 중에 열고 닫을 성격이 아니다.

코드에 선언하면 얻는 것이 셋이다.

- 컴파일 시점에 오타가 잡힌다. 없는 상태를 적으면 빌드가 깨진다
- 테스트가 DB 없이 돈다. 판정 계산을 떼어 낸 것과 같은 이득이다
- 표가 코드 옆에 있어서 전이를 다루는 코드와 같이 읽힌다

DB 에 두는 방법도 저울질했다. 관리자 화면에 표를 보여줄 수 있고 운영 중에 전이를 열 수 있다.
그런데 잘못된 표를 넣어도 실행할 때까지 모른다.
상태 전이가 깨지면 주문이 이상한 상태로 굳고, 굳은 뒤에는 되돌릴 방법이 마땅치 않다.

권한과 다르게 판단한 이유가 이것이다. 권한은 잘못 주면 회수하면 되지만,
전이는 잘못 열면 이미 넘어간 주문이 남는다.

### 따라오는 제약

- `status` 를 직접 바꾸는 경로를 만들지 않는다. 전이 함수 하나만 둔다.
  하나라도 새면 표가 무의미해진다
- 청크 11a 의 상태 × 동작 허용표도 **코드에 둔다.** 전이표와 다른 곳에 두면 상태 규칙이 두 군데로 갈린다
- 전이표를 바꾸려면 배포한다. 그 대신 바꿀 때 테스트가 같이 돈다
- 관리자 화면이 전이표를 보여주려면 코드에서 읽어 API 로 내보낸다. 복사본을 DB 에 두지 않는다
