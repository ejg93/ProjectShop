# 0001. 스키마 변경은 Flyway로 관리한다

- 날짜: 2026-08-03
- 상태: 채택

## 결정

DB 스키마를 `backend/src/main/resources/db/migration` 아래 번호 붙은 SQL 파일로 관리하고,
앱이 뜰 때 Flyway가 순서대로 적용한다. JPA의 `ddl-auto` 는 `validate` 로 두어 엔티티와 실제 스키마가
어긋나면 기동이 실패하게 한다.

## 저울질한 것

| 후보 | 왜 안 골랐나 |
|---|---|
| Liquibase | XML·YAML 체인지로그로 한 겹 추상화한다. DB를 갈아탈 때 이득이지만 Postgres 하나만 쓸 거라 값을 못 치른다 |
| `ddl-auto: update` | 엔티티에서 스키마를 자동으로 뽑아낸다. 컬럼 삭제·이름 변경을 감지 못하고, 무엇이 언제 바뀌었는지 이력이 안 남는다 |
| 수동 SQL 실행 | 적용 여부를 사람이 기억해야 한다. 세션이 끊기는 걸 전제로 만든 저장소에서 제일 먼저 깨진다 |

## 왜 Flyway인가

권한 테이블을 손으로 설계하는 게 이 프로젝트의 목적이라 스키마가 SQL 그대로 보여야 한다.
Flyway는 파일 이름의 버전 번호와 `flyway_schema_history` 테이블로 적용 이력을 남겨서,
DB를 지우고 다시 만들어도 같은 순서로 재현된다.

## 따라오는 제약

- 이미 적용된 마이그레이션 파일은 고치지 않는다. 체크섬이 어긋나면 기동이 막힌다. 바꿀 것은 새 번호로 추가한다
- 엔티티에 필드를 더하면 마이그레이션도 같이 써야 한다. `validate` 가 안 맞으면 앱이 아예 안 뜬다
- 로컬 스키마가 꼬이면 `docker compose down -v` 로 볼륨째 지우고 다시 올린다
