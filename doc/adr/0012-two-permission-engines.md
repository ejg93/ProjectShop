# 0012. 판정 엔진을 두 벌 두고, 운영 판정은 `PermissionEvaluator` 한 벌로 둔다

- 날짜: 2026-10-12
- 상태: 채택
- 청크: `74`(두 번째 구현)·`75`(비교와 이 기록)

## 결정

판정 명세(`D6`, `permission-rules.md`)를 두 구현이 받는다.

| 구현 | 어디서 도나 | 무엇을 하나 |
|---|---|---|
| `PermissionEvaluator`(`4a`) | 서비스가 부른다. 필터체인에는 그것을 감싼 `MetricsAccessManager` 하나가 걸려 있다 | 판정·거부 감사·지표·버튼 목록(`allowedActions`)·범위 떠보기(`covers`)·필드 그룹 |
| `ManagedAuthorizationManager`(`auth.managed`) | **시험의 `Decider` 만 부른다** — 서비스에도 필터체인에도 안 건다 | 같은 표로 같은 답을 내는지 견준다 |

**운영 판정은 `PermissionEvaluator` 한 벌이다.** 두 번째 구현은 운영 코드가 못 부른다 —
`ArchitectureTest.두번째_판정_구현은_운영_코드가_안_부른다` 가 막는다(운영 코드만 잰다). 걸기로 뒤집으면 새 번호로 쓰고 그 규칙을 같이 고친다.

## 견준 결과 — 다른 칸 0

`PermissionMatrixTest` 가 스냅샷 하나(`src/test/resources/snapshots/permission-matrix.md`)를 두 구현에 돌렸다.
198칸이 다 같았다.

| 절 | 칸 | 무엇을 재나 | 다른 칸 |
|---|---|---|---|
| 규칙 하나(부여 2 × 효과 2 × 스코프 3, 대상 6) | 72 | 허용·거부 | 0 |
| 규칙 여럿(순서를 바꾼 짝 포함 8, 대상 6) | 48 | 허용·거부 | 0 |
| 판정 근거(규칙 묶음 6, 대상 6) | 36 | 근거 문자열 | 0 |
| 상태 축(규칙 묶음 4, 상태 3 — `74` 가 더했다) | 12 | 근거 문자열 | 0 |
| 같은 넓이·거부 둘·필드 그룹(묶음 5, 대상 6 — 마무리 60차가 더했다) | 30 | 근거 문자열·보이는 필드 | 0 |

**마지막 절은 첫 판에 없었다.** 앞의 네 절은 규칙에 필드 그룹을 안 달고 같은 넓이의 짝도 없어서, 두 구현이 필드 그룹이나
근거 고르기에서 갈려도 초록이었다(마무리 60차 독립 리뷰). 절을 더한 뒤 스프링 쪽의 「제한 없는 줄이 있으면 전부」를 빼 보니
그 파라미터만 빨갰다.

**`D6` 에 둘을 적었다.** 「같은 넓이면 먼저 읽힌 줄이 근거」와 「거부 근거는 먼저 읽힌 deny」는 코드에만 있었다 —
두 번째 구현이 그것을 코드에서 옮겨 와서 다른 칸으로 안 드러났다. 다른 칸이 나오면 「누가 맞나」가 아니라 「명세가 모호했나」로
읽기로 했으므로(2026-09-23 사용자), 모호했던 그 둘을 「판정 순서」에 적었다. 둘 다 근거 문자열만 정하고 허용·거부와 보이는 필드는
안 바꾼다.

**두 구현이 독립인 정도**: 덮는 범위(`own`·`seller`·`all`)와 넓이는 두 번째 구현이 자기 `switch` 로 다시 적었다
(`Scope.width()` 를 안 빌렸다). 근거 고르기 둘은 위처럼 코드에서 옮겼다. 같이 쓰는 것은 표의 값(`Scope`·`Effect`·`Allowed`)과
이유 문장이다 — 이유 문장은 시험 쪽 `Decider` 가 `Verdict` 갈래마다 같은 문장으로 되옮기므로 **갈래와 이긴 줄이 같은지까지** 잰다.

## 상태 축을 Spring API 로 어떻게 실었나

| 무엇 | 실은 자리 | 근거 |
|---|---|---|
| 대상(주인·셀러·상태) | `RequestAuthorizationContext(request, Map<String, String>)` 의 변수 맵 — `owner_user_id`·`seller_id`·`status` | 7.1.1 에서 값을 싣는 전용 자리이고 값이 문자열이다. 요청 속성(`getRequest()`)은 요청 전체에 퍼지는 자리라 안 썼다 |
| 열린 상태 | 관리자 생성자(`Allowed<String>`) — 동작마다 관리자 하나 | Spring 의 관례가 입구마다 관리자 하나다 |
| 판정 이유·필드 그룹 | `AuthorizationResult` 의 하위 `sealed` `Verdict`(일곱 갈래) | `AuthorizationResult` 는 `isGranted()` 하나뿐이다 |
| 권한 줄·소속 셀러 | `GrantSource` — 판정마다 표를 읽는다 | `ShopUser.getAuthorities()` 가 빈 목록이다. 권한을 세션에 실으면 역할을 바꿔도 다시 로그인할 때까지 옛 권한이 돈다 |

## 필터체인에 왜 안 거나

**대상 행이 필터 단계에 없다.** 실제 필터체인에서 변수 맵은 경로 틀(`/api/orders/{id}`)이 채운다 — 주문 번호는
있어도 주인·셀러·상태는 없다. 그것을 얻으려면 필터가 행을 한 번 읽고 서비스가 또 읽는다. 지금은 서비스가 읽은 행으로
`decide` 를 불러 한 번에 끝난다. 시험에서 변수 맵에 대상을 다 실을 수 있었던 것은 **부르는 쪽이 이미 행을 들고 있어서**다.

**판정에 붙은 일이 `PermissionEvaluator` 에만 있다.** 거부 감사(`4b`)·판정 지표(`Q53`)·버튼 목록·범위 떠보기·필드 그룹으로
응답 깎기가 다 `decide` 와 그 짝에 붙어 있다. **허용된 판정의 결과는 필터 밖으로 안 나간다** — 거부는
`AuthorizationDeniedException` 과 권한 이벤트에 실려 나가지만, 응답을 깎을 필드 그룹이 필요한 것은 허용된 쪽이다.

**Spring API 가 맞는 자리는 이미 쓴다.** 대상 행이 없는 입구 — 지표(`/actuator/prometheus`)가 그렇다 — 는
`MetricsAccessManager` 가 `AuthorizationManager` 를 겉에 두고 안에서 `decide` 를 부른다. 판정은 한 벌이고 Spring 은
입구만 맡는다. 대상이 없는 새 입구가 생기면 이 모양을 따른다.

## 대가

**판정 명세를 바꾸면 두 구현을 같이 고친다.** 한쪽만 고치면 매트릭스가 그 파라미터를 빨강으로 낸다 —
`74` 에서 거부 판정 한 줄을, 마무리 60차에서 필드 그룹 한 줄을 뒤집어 확인했다. **매트릭스에 칸이 있는 것만 잡는다** —
새 축·새 갈래는 매트릭스에 절을 같이 더해야 그 갈림이 보인다. 비용이 비교로 얻는 것보다 커지면 두 번째 구현을 지우는 기록을 새 번호로 쓴다.

**매트릭스가 못 보는 것**: 표를 읽는 길이다. 두 번째 구현의 `GrantSource` 는 운영 구현(JDBC)이 없고 시험이 규칙을 직접
넣는다 — 필터체인에 안 거는 동안 부를 곳이 없어서다. 걸기로 뒤집는 날 그것부터 만든다. 저장값을 `Scope`·`Effect` 로 바꾸는
`of` 가 `auth` 패키지 안이라 그 구현은 `auth` 에 서고, 그날 `ArchitectureTest` 규칙의 방향도 같이 정한다.
