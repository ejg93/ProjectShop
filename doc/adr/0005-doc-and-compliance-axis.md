# 0005. 문서와 법 요건을 청크로 세운다

- 날짜: 2026-08-04
- 상태: 채택

## 결정

계획에 문서 축을 세우고 청크 6개를 추가한다.

| 청크 | 무엇 | 의존 |
|---|---|---|
| D1 | 문서 트리 규약 + 도메인 용어집 | 0 |
| D2 | 법·정책 요건표 | 0 |
| 2a | springdoc-openapi 로 API 스펙 자동 생성 | 2 |
| 3c | 셀러 사업자 정보 컬럼 | 3a, D2 |
| 10a | 거래기록 보존·파기 정책 | 10, D2 |
| 13a | 이용약관·개인정보처리방침·청약철회 문안 | 13, D2 |

청크 11의 의존에 D2를 더했다. 청약철회는 기간이 붙은 상태 전이라 전이표를 짜기 전에 기산점이 정해져야 한다.

## 왜 세웠나

청크 3a까지 만들고 보니 `doc/` 에 ADR 4개와 권한 모델 참조 1개뿐이었다. 전부 "왜 이렇게 짰나" 기록이고,
"무엇을 지켜야 하나" 문서가 없다. 지킬 것을 안 적어 두면 그게 스키마에 반영됐는지 확인할 방법도 없다.

실제로 구멍이 있었다. `seller` 테이블이 `code`·`name`·`status` 뿐인데,
통신판매업자는 상호·대표자·사업자등록번호·통신판매업 신고번호·사업장 주소·연락처를 표시할 의무가 있다.
멀티 셀러라 이 정보가 셀러마다 다르고 상품 상세 화면이 셀러별로 끌어다 써야 한다.
청크 6(상품 스키마)과 14(상품 화면)을 먼저 만들면 나중에 화면과 스키마를 같이 뜯게 된다.

## 법 요건이 설계에 걸리는 자리

D2에서 조문 단위로 정리할 대상이다. 여기 적은 건 어디에 걸리는지의 목록이지 조문 자체가 아니다.

| 요건 | 걸리는 자리 |
|---|---|
| 통신판매업자 신원 표시 | `seller` 컬럼(3c), 상품 상세 화면(14) |
| 청약철회 기간과 기산점 | 주문 상태머신의 전이 조건(11) |
| 거래기록 보존 | 주문·결제 테이블의 삭제 정책(10a) |
| 개인정보 파기 | `app_user` 탈퇴 처리와 보존기간의 분리(10a) |
| 가격 표시 | 상품 가격 컬럼이 무엇을 담는지의 정의(6) |
| 미성년자 거래 취소 | 주문 취소 권한 판정(4, 11a) |

## 이 문서들의 성격

법률 자문이 아니다. 이 프로젝트는 로컬 전용이라 실제 준수 의무의 대상이 아니다.
D2를 두는 목적은 요건이 설계의 어느 지점을 건드리는지를 근거로 남기는 것이다.

조문 번호와 기간 같은 수치는 D2에 출처를 달되, 실제 서비스에 쓸 거면 검증이 따로 필요하다고 문서 안에 명시한다.
확인 안 된 수치를 확정된 것처럼 적으면 이 문서를 두는 의미가 없어진다.

## 저울질한 것

법 요건을 코드 주석으로만 남기는 방법이 있었다. 요건이 걸리는 자리에 바로 붙어서 눈에 띈다는 장점이 있다.
그런데 하나의 요건이 스키마·상태머신·화면 세 군데에 걸리면 주석도 세 군데로 흩어지고,
요건이 바뀌었을 때 세 군데를 다 찾아야 한다. 한 군데 모아 두고 각 지점을 가리키는 편이 낫다.

API 문서를 손으로 쓰는 방법도 저울질했다. 지금은 엔드포인트가 `/api/health` 하나라 손으로 써도 된다.
그런데 청크 7·8부터 API가 붙기 시작하면 손으로 쓴 문서는 바로 코드와 어긋나고,
어긋난 문서는 없는 문서보다 나쁘다.

## 따라오는 제약

- D1·D2는 의존이 0이라 순서상 아무 때나 할 수 있다. 다만 3c·10a·13a는 D2를 선행으로 갖는다
- 3c는 청크 6보다 앞이다. 상품이 셀러를 가리키기 시작한 뒤에 셀러 스키마를 뜯으면 참조가 걸린다
- 10a가 hard delete 를 막으면 그 뒤로 주문·결제를 지우는 모든 경로가 soft delete 를 써야 한다
- 번호에 글자를 붙이는 방식을 이어 간다. 문서 청크는 코드 청크와 축이 달라서 `D` 를 접두어로 썼다
