# 1. 강제력 층위 — 관례·규칙·법 중 무엇이 더 빡빡한가

## 두 축으로 본다

강제력을 하나의 눈금으로 세우면 틀린다. 축이 둘이다.

| 축 | 묻는 것 |
|---|---|
| **강제력의 출처** | 누가 정했나. 우리가 고칠 수 있나 |
| **발견 시점** | 어겼을 때 언제 걸리나 |

두 번째가 실무를 정한다. 법은 강제력이 절대적이지만 **5년 뒤에 걸린다.**
`check` 제약은 우리가 만든 것이라 언제든 지울 수 있지만 **0.1초 뒤에 걸린다.**

## 층위표

| 층 | 정하는 주체 | 어기면 | 걸리는 시점 | 이 프로젝트 |
|---|---|---|---|---|
| 법 | 국가 | 과태료·형사·계약 무효 | 감사·분쟁. 수년 뒤 | `D2` R1~R14 |
| 표준·규격 | 표준화 기구 | 남의 시스템과 안 붙음 | 연동할 때 | HTTP 상태 코드, UTC 저장 |
| DB 제약 | 우리 | 즉시 에러 | 쿼리 실행 순간 | `check`, `references`, `unique` |
| 프로젝트 규약 | 우리 | 아무 일도 안 남 | 사람이 볼 때만 | `D22`, `D23`, `D5` |
| 업계 관례 | 아무도 안 정함 | 아무 일도 안 남 | 안 걸림 | SQL Style Guide, 수수료 4~13% |

## 설계가 하는 일은 층을 내리는 것이다

위층 규칙은 사람이 읽어야 지켜진다. 아래층으로 내려오면 **안 지킬 방법이 없어진다.**

청크 6 이 그 작업이었다.

```
전자상거래법 제17조제2항                      (법)
  → D2 R4 "청약철회 제한 사유를 상품 속성으로"  (규약)
    → product_withdrawal_reason_check         (DB 제약)
```

제한한다고 표시해 놓고 사유를 안 적은 행은 애초에 저장이 안 된다.
사람이 잊을 자리가 사라진 것이다.

`D13` 이 `order` 에 `deleted_at` 을 아예 안 둔 것도 같은 방식이다.
R6 의 5년 보존을 "지우지 말자" 는 약속이 아니라 **지울 컬럼이 없는 구조**로 바꿨다.

**여기서 얻을 것**: 규칙을 문서에 적는 것으로 끝내지 말고,
그것을 강제하는 가장 낮은 층이 어디인지 매번 묻는다. 타입, 제약, 스키마 구조 순으로 내려간다.

## 충돌하면 무엇이 이기나

`법 > 표준 > 규약 > 관례` 가 기본이다. 다만 실제로는 이렇게 통짜로 안 갈린다.

### 관례는 근거가 있으면 버린다

`D22` 가 SQL Style Guide 를 기준으로 잡았는데, 그 가이드의 **복수형 테이블은 버렸다.**
Java 타입과 1:1로 붙이려는 이유였다 — `app_user` ↔ `AppUser`.

같은 가이드의 **"`id` 를 기본 식별자 이름으로 쓰지 말라" 는 따랐다.**

가이드를 통째로 받거나 통째로 버리는 게 아니다. **항목마다 근거를 댄다.**
근거를 못 대면 그건 관례를 따르는 게 아니라 생각을 안 한 것이다.

### 법도 균일하지 않다

강행규정과 임의규정이 갈린다.

전자상거래법 17조는 **강행규정**이라 특약으로 배제가 안 된다.
"이 상품은 환불 불가" 라고 약관에 써도 무효다.

그래서 R4 를 데이터로 뒀다. 법이 인정한 다섯 사유 안에서만 제한할 수 있고,
그 밖은 코드가 아예 못 만든다.

```sql
check (withdrawal_restriction_reason in ('copyable_media', 'made_to_order'))
```

셀러가 자유 텍스트로 사유를 쓸 수 있게 뒀으면, 법이 인정 안 하는 사유가 화면에 나갈 수 있었다.
**열린 값이냐 닫힌 값이냐가 여기서는 법 문제였다.**

다섯 사유 중 앞의 셋(멸실·훼손, 사용으로 인한 가치 감소, 시간 경과)은 안 넣었다.
받은 물건의 상태를 보고 판단하는 것이라 상품 속성이 아니다.
**같은 조문 안에서도 데이터로 표현되는 것과 아닌 것이 갈린다.**

### 법을 그대로 옮기지 않아도 된다

`D8` 이 공급가액과 세액을 저장하지 않는다. 판매가 하나만 두고 필요할 때 역산한다.

세금계산서에는 세액이 필요하다. 그런데 요구는 **결과에 걸리지 저장 방식에 안 걸린다.**
역산으로 같은 값이 나오면 만족한 것이다.

오히려 저장하면 부가세율이 바뀔 때 과거 값이 굳어서 어긋난다.
**법을 문자 그대로 스키마에 베끼는 것이 항상 안전한 게 아니다.**

## 실질 강도를 정하는 진짜 변수 — 되돌릴 수 있나

| 것 | 지금 | 배포 후 |
|---|---|---|
| 마이그레이션 파일 직접 수정 | 가능. 청크 3e 가 했다 | 불가. Flyway 체크섬이 깨진다 |
| DB 컬럼 이름 | 자유 | API 계약이라 못 바꾼다 (`D5` 가 컬럼명=JSON명) |
| 요율 타입 | 오늘 골랐다 | 박제된 주문 데이터가 굳힌다 |

`user_consent.granted` 가 `is_` 규칙을 어긴 채로 남아 있다.
규약이 약해서가 아니라 **되돌리는 비용이 규약을 지키는 값보다 커서다.**
그 컬럼은 `current_consent` 뷰와 응답에 그대로 나간다.

**문서가 코드보다 먼저인 이유도 같다.**
코드는 고치면 되고 문서도 고치면 된다. 그런데 **관례는 한 번 굳으면 다음 사람이 그걸 근거로 삼는다.**
그게 제일 안 되돌려진다. `CLAUDE.md` 의 "문서에 없는 방식이 코드에 먼저 들어가면
다음 사람이 그것을 관례로 본다" 가 이 말이다.

## 한 줄로

강제력의 크기는 법이 제일 크고, **즉시성은 DB 제약이 제일 크고,
안 되돌려지는 정도는 이미 나간 계약이 제일 크다.** 셋을 섞어서 보면 안 된다.

# 2. 수수료율을 정수 만분율(bp)로 고른 이유

## 고른 것

```sql
commission_bp int not null default 1000   -- 1000 = 10.00%
```

대안은 `numeric(5,4)` 로 `0.1000` 을 넣는 것이었다.

## 이유 1 — `D8` 이 금액에서 numeric 을 버린 논리가 요율에도 온다

`D8` 이 금액을 `bigint` 로 정한 이유가 "소수점 이하가 들어갈 여지가 생기고,
그 값이 어디서 들어왔는지 추적이 어려워진다" 였다.

요율은 금액이 아니지만 **곱해서 금액이 된다.** 요율이 소수면 문제가 없어지는 게 아니라
곱셈 결과로 한 단계 옮겨갈 뿐이다.

## 이유 2 — 절사 규칙이 연산 자체에 들어간다

`D8` 의 절사 방식은 **버림**이다. 정수 나눗셈이 곧 버림이다.

```
수수료 = 금액 * commission_bp / 10000
```

`numeric` 이면 이렇게 된다.

```java
price.multiply(rate).setScale(0, RoundingMode.FLOOR)
```

`setScale` 을 부르는 자리가 여러 곳으로 늘고, **한 곳에서 빠뜨리면 조용히 어긋난다.**
정수는 빠뜨릴 `setScale` 이 없다.

규칙을 사람의 규율에 맡기지 않고 연산에 넣는 것 — 위의 「층을 내린다」와 같은 얘기다.

## 이유 3 — 박제 값 비교에 함정이 없다

청크 10 이 주문 항목에 요율을 박제한다. 박제한 값은 나중에 대조 대상이 된다.

`BigDecimal.equals` 는 **스케일까지 본다.**

```java
new BigDecimal("0.10").equals(new BigDecimal("0.1000"))   // false
new BigDecimal("0.10").compareTo(new BigDecimal("0.1000")) // 0
```

같은 요율인데 `equals` 가 false 다. 테스트에서 `assertEquals` 를 쓰면 여기서 터진다.
`compareTo` 를 써야 한다는 걸 아는 사람만 안 틀린다.

정수는 `1000 == 1000` 이다. 알아야 할 것이 없다.

## 이유 4 — bp 는 이미 있는 단위다

만분율(basis point)은 금융에서 표준이다. 1bp = 0.01%.
0.01% 해상도면 수수료율에 충분하고, 우리가 새 단위를 발명한 게 아니라 **아는 사람이 아는 이름**이다.

`_bp` 접미사를 `naming-rules.md` 에 추가했다. 새 접미사를 스키마에 먼저 넣으면
다음 사람이 그걸 관례로 본다는 규칙 때문이다.

## 대가

**화면과 API 에서 100 으로 나눠 보여줘야 한다.** `1000` 을 `10%` 로 바꾸는 변환이 필요하다.

이건 표시 층 한 곳이다. 반면 `setScale` 은 계산이 있는 모든 곳에 걸린다.
**변환 지점이 하나로 모이느냐 흩어지느냐**로 갈렸다.

## 오버플로

`bigint * int / 10000` 이라 중간값이 `bigint` 범위 안에 든다.
금액이 조 단위로 가도 만 배가 `long` 최대치를 안 넘는다. 검사 안 해도 된다.

## 같이 정한 것 — 셀러 기본 요율

`D3` 이 "상품에 요율이 있으면 그 값, 없으면 셀러 기본 요율" 로 정했는데
셀러 쪽 컬럼을 어느 청크도 안 맡고 있었다.

상품 예외만 넣으면 **fallback 대상이 없는 nullable 컬럼**이 된다.
그 상태로 청크 7 을 하면 요율 조회 코드가 10% 를 상수로 박게 되고,
그게 문서에 없는 관례가 되어 굳는다.

`alter table seller add column` 한 줄이라 같은 마이그레이션에 넣었다.
`CLAUDE.md` 의 「드러난 것의 처분」에서 **흡수**에 해당한다.

## 한 줄로

**소수는 자를 시점을 사람이 관리하게 만들고, 정수는 연산이 관리한다.**
돈이 걸린 자리에서는 사람이 관리할 것을 줄이는 쪽이 이긴다.
