# 점검 E — 기준 자료

2026-08-14. `external-references.md` 의 바깥 자료가 **아직 유효한가**를 봤다.
확인일이 2026-08-05 였고 그 뒤로 안 봤다.

**축 다섯 중 마지막이다.** 그리고 유일하게 **우리 코드가 아니라 남의 문서가 대상**이다.

`D22-1`(라이선스 기록)을 여기 합쳤다(사용자 선택) — 같은 문서를 만지므로 링크를 여는 김에 적었다.

## 왜 이 점검이 필요한가

출처 순위(`D23` 축 1)에서 **표준·규격이 2순위**고 프로젝트 규약보다 위다.
그 표준이 개정되면 **우리 규약이 근거를 잃는데 코드는 아무 말도 안 한다.**

실제로 물린 적이 있다 — RFC 9110 이 422 의 이름을 바꿔서 청크 `2d` 가 코드를 고쳤다.

## 훑은 범위

45개 링크 전부를 열지 않았다. **규약이 실제로 기대고 있는 여섯**을 원문으로 대조했다.

나머지(Stripe·Zalando·Spring 처럼 회사가 갱신하는 문서, `D12`·`D17`·`D21` 처럼 청크가 안 온 것)는
다음 점검 E 로 미뤘다. **그 사실을 `external-references.md` 에 적어 뒀다.**

## 안 바뀐 것

| 자료 | 결과 |
|---|---|
| RFC 9457 (`D5`) | 현행. Standards Track, 폐지 안 됨. RFC 7807 을 폐지한 쪽이 이것이다 |
| W3C Trace Context (`D16`) | Level 2 가 후보 권고 초안. **`traceparent` 형식 그대로고 하위호환** — `D16` 안 바뀐다 |
| KWCAG 2.2 (`D20`) | 현행. `KS X OT0003:2022` |
| Flyway | Apache-2.0 그대로 |

## 찾은 것

### 1. NIST SP 800-63B 가 Revision 4 로 개정됐고 우리가 `SHALL` 둘을 못 지킨다

`D14` 가 비밀번호 규칙의 근거로 이 문서를 든다. **개정판을 원문으로 대조했다.**

| 요건 | 등급 | 우리 |
|---|---|---|
| 비밀번호가 **단독 인증수단**이면 최소 **15자** | **SHALL** | **8자 — 미달** |
| 다인수 인증의 일부면 최소 8자 | SHALL | 해당 없음. **MFA 가 없다** |
| **블록리스트 대조**(유출·사전·문맥 단어) | **SHALL** | **없다** |
| 최대 64자 이상 허용 | SHOULD | 64자 — 지킨다 |
| 인쇄 ASCII + 공백 허용 | SHOULD | `\x20-\x7E` — **공백 포함이라 지킨다** |
| 유니코드 허용 | SHOULD | 안 한다. **근거가 있다**(bcrypt 72바이트 절단 구간) |
| 조합 규칙 강제 | **SHALL NOT** | 안 한다 — 지킨다 |

**SHALL 둘이 걸린다.** 우리는 MFA 가 없으므로 비밀번호가 단독 인증수단이고, 그러면 15자가 최소다.

**이건 우리가 임의로 못 정한다.** 출처 2순위라 프로젝트 규약보다 위다. 다만 **8자를 유지할지는
사용자 결정**이다 — 「로컬 전용 학습 프로젝트」를 근거로 벗어날 수 있지만,
`CLAUDE.md` 대전제 1(「실제로 쓰이는 시스템이 가진 확장 형태로 만든다」)와 부딪힌다.

**바꾸면 닿는 곳**: `Password.java`(유일한 출처라 한 곳), `D14`, 데모 시드(`demo-password-1234` 는
19자라 통과), 개발용 테스트 계정(`1` — 통과 못 함, 다만 `local` 전용).
**블록리스트는 새 일**이다 — 목록 출처와 저장 방식을 정해야 한다.

처분: **신규 청크 `D14-1`**.

### 2. OWASP Top 10 이 2025 판으로 바뀌었다

2025-11 발표, 2026-01 최종. `D14` 가 **2021 열 항목**을 청크에 매핑해 뒀다.

```
A01 Broken Access Control            A06 Insecure Design
A02 Security Misconfiguration        A07 Authentication Failures
A03 Software Supply Chain Failures   A08 Software or Data Integrity Failures
A04 Cryptographic Failures           A09 Security Logging and Alerting Failures
A05 Injection                        A10 Mishandling of Exceptional Conditions
```

우리에게 걸리는 것이 셋이다.

**`A10 Mishandling of Exceptional Conditions` 가 신규다.** 우리 설계가 정면으로 걸리는 자리가 여럿이다 —
`ApiExceptionHandler` 의 번역, `ShopException` 한 종류, `Retries.onConflict`,
**Redis 강등(fail-open)**, 캡차 fail-open. `D14` 에 이 항목 자체가 없다.

**`A03 Software Supply Chain Failures` 가 3위다.** 2021 의 「Vulnerable and Outdated Components」를
흡수·확장한 것이고, **의존성 검증 절차가 우리에게 없다.** 위 라이선스 표가 그 축의 절반이다.

**`A09` 가 「Logging and **Alerting**」으로 바뀌었다.** 알림이 이름에 들어왔고 우리는 없다(`D18` 미착수).
`D16` 이 「`ERROR` 는 사람이 개입할 것에만」이라고 정해 뒀는데 **그 사람에게 닿는 경로가 없다.**

처분: **`D14-1` 이 같이 한다.** 매핑을 2025 로 다시 그리는 일이라 같은 문서를 두 번 고칠 이유가 없다.

## 곁가지 — 라이선스를 기록했다

`D22-1` 을 합쳐서 `external-references.md` 에 절을 만들었다.

- **인용 자료 5종**: SQL Style Guide 가 CC BY-SA 4.0 이라는 것이 `coding-rules.md` 안에만 있었는데 옮겼다
- **의존성 12종**: 전부 Apache-2.0 / BSD-2 / MIT. **GPL 계열 0건**

`D23` 이 「판단한 적 없는 것과 판단해서 괜찮은 것은 다르다」고 쓴 그 판단을 이제 기록으로 남겼다.

## 관찰

### 이 축만 시간이 지나면 저절로 틀려진다

다른 넷은 우리가 코드를 안 건드리면 결과가 안 바뀐다. **이 축은 가만히 있어도 틀려진다** —
남이 문서를 고치기 때문이다.

두 달 반 만에 **핵심 근거 여섯 중 둘이 개정**됐다. 그러니 점검 E 는 **한 번 하고 끝나는 것이 아니라
주기로 도는 것**이고, 다음 회차가 언제인지를 정해 두지 않으면 안 돈다.

### 이 점검이 못 잡는 것

**우리가 인용한 줄이 그 문서 안에서 바뀐 경우**는 목차만 봐서는 안 보인다.
이번에는 NIST 를 문장 단위로 대조해서 `SHALL` 을 잡았지만, 나머지는 「현행인가」까지만 봤다.
