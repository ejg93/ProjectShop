## 발견 — 고칠 것

### 1. 완료 표시가 42개 중 6개뿐이었다

재개 절차는 **`PLAN.md` 의 분할표에서 다음 미완료 청크를 잡는다.**
그런데 완료된 42개 중 36개가 표시 없이 남아 있었다. **표만 봐서는 무엇이 끝났는지 알 수 없고,**
매번 `PROGRESS.md` 이력 67행을 훑어야 알 수 있는 상태였다.

토큰을 아끼려고 만든 저장소에서 이건 그냥 낭비다. 이번 점검에서 일괄 표시했다.

### 2. 계정 관리 축이 HTTP 층에 없다

`HttpFlowTest` 는 가입·로그인·권한·감사·로그아웃을 덮는다.
그 뒤에 만든 **계정 조회·동의 철회·탈퇴는 안 덮는다.**

특히 **탈퇴의 두 기기 시나리오**(A 에서 탈퇴하면 B 도 끊긴다)는 손 `curl` 로만 확인했다.
`ADR 0010` 의 핵심이 정확히 그것인데, 회귀로 깨져도 알 방법이 없다.
1차가 지적한 "손 검증은 자동이 아니라 회귀를 못 잡는다" 가 새 코드에서 되살아났다.

청크 `35b` 로 세운다.

## 발견 — 관찰

### 3. 부채가 줄지도 늘지도 않았다

| 부채 | 1차 | 2차 |
|---|---|---|
| 알려진 구멍(`permission-rules.md`) | 3 | 3 |
| 미착수 기준 문서(D12·D17~D21) | 6 | 6 |

새로 쌓이지 않은 것은 좋다. 다만 **「구멍 3: 스코프가 목록 조회에 안 걸린다」가 아직 살아 있다.**
`4b-1` 이 첫 목록 API 였지만 `audit:read` 가 `all` 스코프뿐이라 누출이 성립하지 않았다.
**상품 조회(청크 8)가 이 구멍을 실제로 밟는 첫 자리다.**

### 4. 단위 층이 얇다

테스트 클래스 18개 중 단위가 2개, 통합이 15개, HTTP 가 1개다.

지금은 맞다. 판정 계산 말고는 DB 없이 검증할 만한 순수 로직이 없다.
상품 가격·수수료 계산(`D8`)이 오면 단위 층이 늘어야 정상이고, **안 늘면 그때가 신호다.**

### 5. 응답 형식 일관성은 아직 검증할 게 없다

snake_case 와 Problem Details 가 전역 설정이라 엔드포인트마다 갈릴 여지가 없다.
목록 규약(`items`·`page`·`size`·`total`)은 쓰는 곳이 `4b-1` 하나뿐이다.
**두 번째 목록 API 가 나올 때 비교 대상이 생긴다.**
