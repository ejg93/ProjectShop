`D22` 명명 규칙과 `D23` 코딩 규약을 세운 직후, **그 규칙들이 나오기 전에 쓴 코드**를 훑었다.
2026-08-07. main 2,246줄 · 테스트 3,864줄이 대상이다.

규약을 만들면서 한 조사는 계층·예외·트랜잭션·`record`·패키지 의존까지였다.
여기서는 그때 안 본 것을 본다.

## 고친 것

### 1. 비밀번호 규칙이 두 곳에 있었다

`AuthController`(가입)와 `MeController`(변경)가 각각 `@Size(min=8,max=64)` 와 ASCII 패턴을 들고 있었다.
`D14` 가 정한 규칙인데 출처가 둘이었다.

**주석에 위험을 적어 두고 중복을 남긴 상태였다** — "두 곳이 갈리면 가입은 되는데 변경이 막힌다".

터지는 방식이 구체적이다. 비밀번호 재설정(`5c`)을 만드는 사람이 둘 중 어느 쪽을 베낄지 모른다.
갈려 있으면 자기 것을 새로 만들고, 그러면 정의가 셋이 된다.
나중에 `D14` 를 고칠 때 둘만 고치고 하나를 놓치면 **입구마다 보안 규칙이 다른 상태**가 되는데,
각 입구는 자기 규칙대로 잘 동작하므로 **테스트가 안 잡는다.**

상수로 뽑는 것으로는 부족하다. 값은 모이지만 **조합이 안 모여서** 새 자리에서
`@Size` 만 붙이고 `@Pattern` 을 빠뜨릴 수 있다. 규칙 단위로 묶었다.

```java
@NotBlank @Password String newPassword
```

`Password.java` 가 `D14` 의 유일한 출처다.

### 2. `@DisplayName` 이 없는 테스트가 하나 있었다

`BackendApplicationTests.contextLoads`. 청크 2 에서 만든 것이라 규약보다 먼저다.
이름을 붙이면서 **왜 단언이 없는 것이 맞는지**를 주석으로 남겼다.

### 3. 미사용 import 두 개

`Pattern` 을 `@Password` 로 옮기면서 남았다.

## 문서를 고친 것

**규약이 현실보다 강했던 자리 둘.** 코드를 문서에 맞추는 대신 문서를 고쳤다.

### `.as()` 를 모든 단언에 붙이라고 적혀 있었다

실제는 213개 중 64개(30%)다. `status().isOk()` 처럼 이름만으로 뜻이 서는 단언에까지 붙이면
노이즈만 는다. **"깨진 이유가 안 드러나는 단언에 붙인다"** 로 고쳤다.

### `D22` 의 Java 명명 표가 실제 코드보다 좁았다

`Criteria`·`Page`·`Row`·`Decision`·`Target` 같은 값 객체 이름이 표에 없었다.
쓰이고 있는 관례를 표에 추가했다. **표에 없는 이름이 코드에 먼저 들어가면
다음 사람이 그것을 관례로 본다.**

## 안 고치고 남긴 것

전부 이유가 있고 처분처가 정해져 있다.

| 남긴 것 | 왜 | 어디서 |

| 기존 13개 테이블의 `id` | 얻는 것이 일관성뿐 | 안 고침 |
