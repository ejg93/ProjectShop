# 점검 D — 프론트

2026-08-14. `D24`(프론트 계층)와 `D20`(화면·문구)을 잣대로 `frontend/src` 751줄 14파일을 훑었다.

**화면 축이 이제 막 열려서 대상이 짧다.** 어긋난 것을 지금 고치는 값이 제일 싸다 —
화면이 열넷이 되면 같은 점검이 다섯 배다.

| 항목 | 결과 |

### 대비비를 직접 계산했다

`D20` 이 본문 4.5:1 을 요구하고 **그 출처가 스킬이 아니라 법**이라(장애인차별금지법 → KWCAG 2.2)
눈으로 넘기지 않고 WCAG 상대휘도 공식으로 계산했다.

| 짝 | 비 |
|---|---|
| 본문 `--text` / `--surface` | 통과(아주 높다) |
| 흐린 글 `--text-muted` / `--surface` | 약 **7.4** |
| 버튼 `--accent-on` / `--accent` | 약 **7.0** |
| 오류 `--danger-text` / `--surface` | 약 **6.3** |
| 다크 강조 `--accent-text` / `--surface` | 약 **10.1** |
| 다크 흐린 글 `--text-muted` / `--surface` | 약 **7.5** |

**전부 4.5 를 넘는다.** 다크모드에서 `--accent-text` 를 따로 올려 둔 것(`#9f1239` → `#fda4af`)이
실제로 값을 한다 — 안 올렸으면 2.5 라 본문 기준에 못 미친다.

## 찾은 것

### 1. 로그인 실패가 두 입력칸을 모두 「잘못됨」으로 표시한다

```tsx
<Field name="email"    invalid={error !== null} ... />
<Field name="password" invalid={error !== null} ... />
```

`invalid` 가 `aria-invalid` 로 간다. 그런데 **로그인 실패는 어느 칸이 틀렸는지 모르는 오류**다 —
서버가 일부러 안 가른다(`D14`, 가입 여부를 물어보는 도구가 되지 않게).

**화면낭독기가 이메일 칸을 「잘못된 입력」이라고 읽는데 이메일은 맞았을 수 있다.**
`aria-invalid` 는 「이 필드의 값이 유효하지 않다」는 뜻이라 사실과 다른 것을 말한다.

`D20` 의 오류 자리 표로 보면 이 오류는 **「그 입력칸의 값이 규칙에 안 맞음」이 아니라
「요청은 옳은데 지금 상태가 안 맞음」** 쪽이다. 그쪽은 인라인이 아니다.

**규칙이 이 경우를 안 다룬다.** 표에 「어느 칸인지 서버가 안 알려주는 오류」라는 줄이 없다.
`D20` 을 먼저 고치고 화면을 맞춰야 한다(`D23` 「이 문서를 고칠 때」).

처분: **신규 청크 `13h`**.

### 2. 건너뛰기 링크가 `<main>` 을 안 가리킨다

`layout.tsx` 가 `<div id="main">` 으로 감싸고 각 페이지가 그 안에 `<main>` 을 그린다.
건너뛰기 링크의 `href="#main"` 은 **감싸는 `div`** 에 닿는다.

동작은 한다 — 초점이 그 자리로 가고 그 아래가 본문이다.
다만 **의미 표지(landmark)는 안쪽 `<main>`** 이라, 표지로 이동하는 보조기술은 두 자리를 본다.

처분: **`13h` 가 같이 본다.** 고치는 방법이 둘이고(레이아웃이 `<main>` 을 그리거나,
`id` 를 안쪽으로 옮기거나) **`ComingSoon` 이 `main` 을 그리는 구조와 얽혀 있다.**

### 3. `D24` 의 서버 입구가 아직 없다

`api.ts` 에 브라우저 입구 하나뿐이다. **위반이 아니라 미착수** —
공개 데이터를 서버에서 그리는 화면이 아직 없고, 청크 `14` 가 그 입구를 만든다.

여기 적는 이유는 **`D24` 를 읽고 코드를 보면 없어서 헷갈리기 때문**이다.

## 관찰

### 화면 축은 규칙이 먼저 선 상태로 시작했다

`13-0`(디자인 스킬)·`D20`·`D24` 가 코드보다 앞섰고, 그 결과가 이 점검의 표에 그대로 나온다 —
**접근성 항목이 전부 초록이다.** 나중에 붙였으면 「고치는 것이 아니라 다시 짜는 것」이 됐을
항목들이다(`D23` 「접근성」).

백엔드와 비교가 된다. 백엔드는 규칙이 코드 뒤에 와서 `checkpoint-3-rules` 가 두 가지를 고쳤다.

### 이 점검이 못 잡는 것

**보이는 것을 안 봤다.** 실제로 렌더된 화면의 초점 순서, 낭독 순서, 축소 화면의 배치는
코드만 읽어서 판정이 안 된다. Puppeteer 로 밟을 수 있지만(`stack.md`) 이번엔 안 했다.

`D20` 이 「수동 스크린 리더 검증」을 「청크가 서면 그때」로 미뤄 둔 것과 같은 자리다.
**화면이 늘면 그 청크를 세워야 한다.**
