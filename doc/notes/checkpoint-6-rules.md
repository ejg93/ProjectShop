# 점검 C — 규약·코딩 축

2026-08-14. `D22`·`D23` 를 잣대로 **코드에서 규칙으로 올라가며** 훑었다.
점검 A·B 와 방향이 반대다 — 어긋난 것이 코드 안에 있어서 훑으면 나온다.

`checkpoint-3-rules`(2026-08-07) 이후 두 번째다. **그때 대상이 main 2,246줄이었고 지금 8,689줄**이라
3.9배고, 그 사이 규칙도 늘었다(축 1 「플랫폼 사실」, 축 2 「안 나가게 하는 것」, 패키지 경계).

## 지켜지고 있던 것

| 항목 | 결과 |
|---|---|
| 계층 — 컨트롤러가 `JdbcClient` 를 직접 쓰나 | `HealthController` 하나. **문서가 적어 둔 예외 그대로** |
| 트랜잭션 경계가 서비스인가 | 컨트롤러에 `@Transactional` 0건 |
| 서비스가 웹을 아나 | `ResponseStatusException`·`HttpStatus` 0건 |
| `select *` | 0건 (`count(*)` 만) |
| SQL 에 값 이어붙이기 | 0건. 정렬만 문자열이고 허용 목록을 지난다 |
| `Map<String,Object>` 로 행 받기 | 0건. 쓰이는 곳은 감사 `detail` (JSONB **한 컬럼**이라 행이 아니다) |
| DTO 가 `record` 인가 | `class ...Request/Response/Item/Page/Row` 0건 |
| 시각을 `singleRow()` 로 읽나 | 0건 |
| 축약 이름(`cnt`·`usr`·`svc` 등) | 0건 |
| 매직 넘버 | 0건 |
| `@DisplayName` 누락 | 0건 (`@Test` 516 / `@DisplayName` 686) |
| 마이그레이션에 `alter` 쌓기 | 0건 |
| 빈 값에 뜻 싣기 | 0건. `Allowed<T>` 를 쓰고 `Set` 은 실제 목록에만 |
| 의존성에 GPL 계열 | 0건 |

**8,689줄이 규약을 대체로 지킨다.** 3.9배로 불어나는 동안 새로 생긴 위반이 아래 넷뿐이다.

## 찾은 것

### 1. 필드 그룹 코드가 생 문자열이다

```java
decision.canSee("basic")      AccountService
decision.canSee("contact")    AccountService
decision.canSee("shipping")   OrderQuery · SellerOrderQuery
```

값 목록이 DB(`permission_field_group.code`)에 있고 **코드가 그 값으로 분기한다.**
`D23` 의 물음(「값이 늘었을 때 코드를 안 고쳐도 동작하나」)에 **아니다**다 — 그룹이 늘면
응답에 필드를 더해야 하므로 어차피 배포한다.

**실패가 조용하다.** 오타를 내면 `canSee` 가 `false` 를 돌려주고 **그 필드가 응답에서 빠진다.**
막히는 쪽이라 안전하지만 **오류도 로그도 안 남고**, 화면에는 「볼 수 없는 필드」와 구분이 안 된다
(`D20` 이 그 둘을 갈라 놓았는데 여기서 뭉개진다).

처분: **신규 청크 `4g`**.

### 2. `me` 패키지가 관객 단위다

패키지 경계 규칙(`D23`, 어제 세움)은 **자원 단위로 파고 관객은 클래스로 가른다**고 정했다.
`me` 는 자원이 아니라 관객("나")이다.

| 파일 | 실제로 다루는 자원 |
|---|---|
| `AccountService`·`WithdrawalService` | `app_user` |
| `AccountPurgeService` | `app_user`·`user_consent` |
| `ConsentService` | `consent_item`·`user_consent` |
| `ConsentItemController` | `consent_item` — **로그인 전에 부르는 공개 조회**라 「나」와 맞지도 않는다 |

자원으로 자르면 `account` 와 `consent` 둘이다.

**이 규칙은 어제 내가 정한 것**이고(사용자에게 안 물었다), 정하자마자 기존 코드 하나를
위반으로 만든다. 선택지가 둘이다 — 규칙을 지키고 옮기거나, 규칙에 예외를 적거나.

처분: **신규 청크 `5l`.** 사용자가 「수정 방향을 정할 청크가 생기긴 하겠네」로 이미 예고했다.

### 3. `D22` 가 1:1 확장 표의 기본키를 안 다룬다

기본키가 `<테이블>_id` 가 아닌 것이 넷이다. 훑을 때는 둘이 미설명으로 보였는데
**문서를 정확히 읽으니 하나였다.**

| 기본키 | `D22` 가 덮나 |
|---|---|
| `app_user.user_id` | 덮는다 — 예약어 접두사 표는 엔티티 이름을 쓴다 |
| `shop_order.order_id` | **덮는다** — 같은 규칙이다(`order` 가 예약어). 예로 안 적혔을 뿐 |
| `holiday.holiday_date` | 덮는다 — 값 자체가 식별자다 |
| **`order_shipping.order_id`** | **안 덮는다** — 1:1 확장 표라는 종류가 문서에 없다 |
| `flyway_schema_history.installed_rank` | 우리 것이 아니다 |

`order_shipping` 은 주문당 배송지가 하나라 본체의 기본키를 그대로 쓴다.
대리키를 얹으면 아무도 안 쓰는 번호가 생기고 「주문당 하나」를 유니크 제약으로 따로 적게 된다 —
바로 아래 「값 자체가 식별자인 표」와 같은 논리인데 **그 절이 달력·코드표만 예로 들었다.**

처분: **`D22` 를 고쳤다.** `shop_order` 를 예로 덧붙이고 1:1 확장 표를 절로 넣었다.

### 4. 라이선스를 적으라는 자리가 비어 있다

`D23` 이 「인용 자료의 저작자·라이선스를 `external-references.md` 에 같이 적는다」고 정했는데
**그 파일에 라이선스가 한 줄도 없다.** `D23` 이 직접 든 예(SQL Style Guide 가 CC BY-SA 4.0)조차
`coding-rules.md` 안에만 있다.

의존성 쪽은 훑어서 **GPL 계열이 없는 것은 확인**했지만, **확인한 기록이 없다** —
`D23` 이 「판단한 적 없는 것과 판단해서 괜찮은 것은 다르다」고 쓴 그 상태다.

처분: **신규 청크 `D22-1`**(문서 축이라 번호를 그쪽에 붙였다).

## 안 고치고 남긴 것

| 남긴 것 | 왜 | 어디서 |
|---|---|---|
| `user_consent.granted` 에 `is_` 가 없다 | 응답에 그대로 나가서 이름만 고치면 API 가 바뀐다 | 안 고침(`checkpoint-3-rules` 와 같은 판단) |
| `role.code`·`seller.code` 유니크가 자동 이름 | 얻는 것이 일관성뿐이다 | 안 고침(점검 B) |
| `app_user.status`·`seller.status` 생 문자열 | 점검 B 가 이미 처분했다 | `11-5` |

## 관찰

### 새 규칙이 즉시 위반을 만든다

찾은 넷 중 **둘이 어제 세운 규칙에 걸렸다**(`me` 패키지, 라이선스 기록).
규칙을 코드에서 뽑아 세웠는데도 그렇다 — **뽑을 때 본 범위가 좁았기 때문**이다.
패키지 경계는 `product` 하나를 보고 세웠고 `me` 를 안 봤다.

**규칙을 세운 직후에 점검을 붙이는 것이 값을 한다**는 뜻이다. `checkpoint-3-rules` 가
`D22`·`D23` 직후에 돌았던 것과 같은 자리다.

### 이 점검이 못 잡는 것

**기계로 못 읽는 규칙은 안 잡힌다.** `D23` 의 「주석은 왜 그렇게 했는지를 적는다」,
「알고 남기는 구멍은 반드시 적는다」, `D15` 의 층 배치가 그렇다.
`.as()` 를 붙일 자리인지도 사람이 읽어야 갈린다.

이번에는 **grep 으로 판정되는 것만** 훑었고, 그 사실을 적어 둔다.
