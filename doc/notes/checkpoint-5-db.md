# 점검 B — DB 제약 축

2026-08-14. 점검 A 가 채운 `D2` 대장의 이름들이 **스키마에 실재하는지**, 그리고 반대로
**스키마에 있는데 근거가 없는 것**이 있는지 봤다. 살아 있는 DB(`shop-db`)에 직접 물었다.

**축 다섯 중 DB 제약 축은 이번이 처음이다.**

## 왜 이 점검이 필요한가

이 저장소는 배포 전이라 마이그레이션의 `create` 문을 직접 고친다(`D23` 「마이그레이션」).
`V16`·`V17` 을 실제로 그렇게 고쳤다. **제약 한 줄이 그 과정에서 빠져도 테스트도 로그도 안 알려 준다.**

## 깨끗한 것

| 무엇 | 결과 |
|---|---|
| 이름 붙은 `check`·`unique` | **55 선언 / 55 실재.** 사라진 것 0, 근거 없는 것 0 |
| 트리거 | **16 선언 / 16 실재** |
| 금액·수량 컬럼의 `check` | **16 / 16.** `amount`·`price`·`fee`·`total`·`count`·`quantity`·`bp` 로 끝나는 컬럼 전부 |
| `updated_at` 이 있는 표의 갱신 트리거 | **9 / 9.** 트리거 없이 안 바뀌는 컬럼이 없다 |
| `payment` 필드 그룹(`R8`·`R18`) | 셀러·감사자에 **안 붙어 있다.** 고객만 본다 |
| `deleted_at` 의 배치(`R6`) | `app_user`·`product`·`seller`·`sku` 넷. **`shop_order` 에는 없다** — 지울 컬럼이 없는 구조 |

**점검 A 의 대장에 적힌 이름 중 없는 것은 하나도 없었다.**

## 찾은 것

### 1. 주문 축의 상태 목록에 방벽이 없다

`D23` 이 「`check` 와 enum 이 두 사본이라 어긋날 수 있으니 **제약 정의를 읽어 대조하는 테스트를 둔다**」
고 정했다. **상품 축은 `7e` 가 맞췄는데 주문 축은 안 맞췄다.**

값 목록을 가진 우리 `check` 가 12개고 대조 테스트가 붙은 것은 4개다.

| 제약 | 대응 enum | 대조 테스트 |
|---|---|---|
| `product_status_check` | `ProductStatus` | 있다 |
| `sku_status_check` | `SkuStatus` | 있다 |
| `product_withdrawal_reason_check` | `WithdrawalRestrictionReason` | 있다 |
| `seller_exempt_reason_check` | `MailOrderExemption` | 있다(`14a`) |
| **`shop_order_status_check`** | **`OrderTransitions.Payment`** | **없다** |
| **`seller_order_status_check`** | **`OrderTransitions.Shipment`** | **없다** |
| **`order_status_history_status_check`** | **위 둘 다** | **없다** |

**지금은 갈리지 않았다.** 직접 대조해서 확인했다 — `Payment` 4개와 `Shipment` 7개가
제약의 목록과 정확히 같다.

**사본이 여섯이다.** enum 둘 + `shop_order` + `seller_order` + `order_status_history` 안에 둘.
이력 제약이 `case` 로 갈려서 같은 목록을 한 번 더 적는다.

**상품 축보다 주문 축이 더 위험한데 방벽이 거기만 없다** — 상태가 더 많고, 전이표가 있고,
상태 축 권한(`11a`)까지 그 목록에 걸려 있다.

처분: **신규 청크 `11-5`**.

### 2. 계정·셀러 상태가 Java 에서 생 문자열이다

```java
"active".equals(rs.getString("status"))   // ShopUserDetailsService
```

`app_user_status_check`·`seller_status_check` 가 값 목록을 갖고 있고 **코드가 그 값으로 분기한다.**
`D23` 의 물음(「값이 늘었을 때 코드를 안 고쳐도 동작하나」)에 **아니다**라서 `check` + enum 이어야 한다.

`7e` 가 상품 축에서 치운 것과 **같은 모양**이다.

**`D23` 의 「지금 어긋난 곳」이 비어 있다고 적혀 있는데 안 비었다.** 그 절을 고쳐야 한다.

처분: **`11-5` 가 같이 한다.** 다만 **전면 확인은 점검 C** 다 — 생 문자열이 더 있는지는
코드에서 올라가며 훑어야 나온다.

### 3. 유니크 둘만 이름을 안 붙였다

`role.code` 와 `seller.code` 가 인라인 `unique` 로 선언돼서 Postgres 가 이름을 지었다
(`role_code_key`·`seller_code_key`). 나머지 53개는 전부 `constraint <이름>` 으로 명시했다.

**위험은 낮다** — Postgres 의 자동 이름이 `<표>_<컬럼>_key` 로 결정적이고, 우연히 우리 관례와 같다.
다만 **대장이 이름으로 가리키는 이상 그 이름이 우리 것이어야** 일관된다.

처분: **안 고친다.** 고치려면 마이그레이션을 건드리고 DB 를 다시 만들어야 하는데
얻는 것이 일관성뿐이다(`checkpoint-3-rules` 가 기존 `id` 컬럼에 내린 것과 같은 판단).

### 4. `PROGRESS` 의 마이그레이션 수가 낡았다

「`applied_migrations` **18**(마이그레이션 17 + 시드)」로 적혀 있는데 실제는 **19** 다.
시드가 둘이 됐다(`V900__demo_seed`·`V901__test_account`).

처분: **고쳤다.**

## 관찰

### 대장이 실제로 값을 했다

점검 A 가 이름을 적어 둬서 이 점검이 **추적 없이 조회만으로** 끝났다.
대장이 없었으면 요건마다 코드를 다시 뒤져야 했다.

### 이 점검이 못 잡는 것

**제약이 있는지**는 봤지만 **제약이 옳은지**는 안 봤다. 예를 들어
`sku_price_check` 가 `>= 0` 인 것은 확인했지만 그 값이 부가세 포함가여야 한다는 것(`R12`)은
제약으로 표현돼 있지 않고, 그건 점검 A 가 이미 찾아 `D2-2` 로 세웠다.

**코드에만 있는 규칙도 안 잡힌다.** 생 문자열 비교를 하나 발견했지만
그건 제약을 훑다 걸린 것이지 이 방향이 찾아 주는 것이 아니다. 점검 C 가 그 방향이다.
